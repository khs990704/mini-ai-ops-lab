## 코드 및 설정 의도

- Day 1에는 실행 가능한 Python 코드를 작성하지 않았다. `src/`는 Day 2 학습 코드가 들어갈 위치만 준비했다.
- `.env.example`은 실제 비밀정보 없이 안전한 로컬 설정 형식을 보여준다.
- `requirements.txt`는 향후 학습 모델과 YAML 설정 로딩에 필요한 최소 의존성을 설명한다.
- `.gitignore`는 실행 중 생성되는 로그와 모델 파일을 제외하면서 `.gitkeep`으로 필요한 디렉터리 구조를 유지한다.
- `README.md`는 모델 정확도보다 설정, 실행 상태, 로그, artifact를 추적하는 운영 목적을 먼저 설명한다.
- 설명 주석은 문법을 반복하지 않고 설정이나 코드가 존재하는 이유를 한글로 전달하도록 정했다.

## 실행한 명령과 목적

### `mkdir -p configs src logs artifacts`

- 목적: 프로젝트가 사용할 네 기본 디렉터리를 준비한다.
- 변경 여부: 디렉터리가 없으면 생성하는 변경 명령이다. 이미 존재하는 디렉터리와 내부 파일은 삭제하거나 덮어쓰지 않는다.
- 실행 결과: `configs/`, `src/`, `logs/`, `artifacts/`가 준비됐다.
- 성공 기준: 오류 메시지 없이 exit code 0으로 끝나고 네 디렉터리가 존재한다.

### `find configs src logs artifacts -maxdepth 2 -type f | sort`

- 목적: 네 기본 디렉터리에 저장된 파일을 확인한다.
- 변경 여부: 파일을 읽어 목록만 출력하는 명령이다.
- 실행 결과: 각 디렉터리에 `.gitkeep`이 존재함을 확인했다.
- 성공 기준: `artifacts/.gitkeep`, `configs/.gitkeep`, `logs/.gitkeep`, `src/.gitkeep`이 출력된다.

### `git check-ignore -v --no-index .env logs/runs.jsonl artifacts/example/model.pkl`

- 목적: 비밀 설정, 실행 로그, 모델 artifact에 어떤 `.gitignore` 규칙이 적용되는지 확인한다.
- 변경 여부: 무시 규칙만 조회하며 대상 파일을 생성하거나 변경하지 않는다.
- 실행 결과: `.env`, `logs/*`, `artifacts/*` 규칙이 각각 적용됨을 확인했다.
- 성공 기준: 세 대상과 일치한 `.gitignore` 규칙 및 줄 번호가 출력되고 exit code 0으로 끝난다.

파일 탐색, 문서 제목 검색, Markdown 링크 검사, diff 서식 확인에 사용된 내부 보조 명령은 프로젝트를 실행하거나 운영할 때 재사용할 명령이 아니므로 이 목록에서 제외했다. 내부 검사에서 발견한 실제 문제와 해결 결과는 아래 `발견한 문제`와 `검증 결과`에만 기록했다.

## 검증 결과

- `.env`, `logs/runs.jsonl`, `artifacts/example/model.pkl`이 `.gitignore` 규칙에 따라 제외됨을 확인했다.
- 한글 설명 주석을 추가한 뒤 Git 무시 동작이 변하지 않았음을 확인했다.
- README의 한글 목차와 내부 문서 링크 대상이 존재함을 확인했다.
- 위키의 영문 섹션 제목이 제거되고 내부 Markdown 링크가 모두 유효함을 확인했다.
- 모든 서식 수정 후 `git diff --check`가 exit code 0으로 통과했다.
- Day 1에는 실행 코드가 없으므로 의존성 설치와 학습 실행은 Day 2로 미뤘다.

## 직접 확인 방법

아래 명령은 모두 WSL의 프로젝트 root에서 실행한다.

```bash
cd /home/hskim/project/mini-ai-ops-lab
```

`cd`는 shell의 현재 작업 위치만 변경하며 프로젝트 파일은 수정하지 않는다.

### 1. 기본 디렉터리 구조 확인

```bash
find configs src logs artifacts -maxdepth 2 -type f | sort
```

목적은 네 기본 디렉터리에 placeholder가 존재하는지 직접 확인하는 것이다. 파일을 변경하지 않으며 다음 경로가 출력되면 정상이다.

```text
artifacts/.gitkeep
configs/.gitkeep
logs/.gitkeep
src/.gitkeep
```

### 2. Git 무시 규칙 확인

```bash
git check-ignore -v --no-index .env logs/runs.jsonl artifacts/example/model.pkl
```

파일을 생성하지 않고 무시 규칙만 확인한다. `.env`, `logs/*`, `artifacts/*`에 해당하는 `.gitignore` 줄이 각각 출력되면 정상이다.

Day 1에는 실행 가능한 학습 코드가 없으므로 아직 내가 모델 학습을 실행해 확인할 명령은 없다.

## Codex Q&A

- 질문: `.gitkeep`은 무엇이고 왜 제안했는가?
  답변: Git은 빈 디렉터리를 추적하지 않는다. `.gitkeep`은 `logs/`와 `artifacts/` 같은 기본 구조를 clone 후에도 유지하기 위한 관례적인 placeholder다. 실제 로그와 모델 파일은 `.gitignore`로 제외한다.
- 질문: `configs/`, `src/`, `logs/`, `artifacts/`는 각각 어떤 용도인가?
  답변: `configs/`는 실행 설정, `src/`는 실행 코드, `logs/`는 실행 과정과 상태 기록, `artifacts/`는 학습으로 생성된 모델과 결과물을 담당한다. 설정과 코드가 실행되면 로그와 artifact가 만들어지는 구조다.

## 발견한 문제

- 첫 번째 `git diff --check`가 `.gitignore` 파일 끝의 불필요한 빈 줄을 보고하고 exit code 2로 실패했다.
- `.gitignore` 초안에서 기존 type 검사, build, coverage 결과 제외 규칙이 빠진 것을 최종 diff 검토에서 발견했다.
- 첫 작업 흐름은 구현 직후 위키와 작업 일지를 작성하여 후속 Q&A를 기록하기 어려웠다.
- 위키 한글화 후 7개 파일 끝에 불필요한 빈 줄이 있어 `git diff --check`가 다시 exit code 2로 실패했다.
- 작업 일지를 내 프로젝트 수행 관점으로 작성한다는 기준과 어떤 명령을 설명할지에 대한 범위가 처음에는 명확하지 않았다.

## 수정 또는 결정

- `.gitignore`의 추가 빈 줄을 제거하고 기존 제외 규칙을 복원했다.
- 작업을 작은 단계로 나누고 각 단계마다 직접 승인하고 검수할 때까지 기다리도록 영구 지침을 변경했다.
- 위키와 작업 일지는 전체 구현 검수와 Q&A가 끝난 뒤 별도 승인을 받아 갱신하도록 정했다.
- 설명 주석, README, 기술 위키, 작업 일지는 한글로 작성하되 기술 식별자는 필요한 경우 원문을 유지하기로 했다.
- 위키 파일 끝의 추가 빈 줄을 제거한 뒤 서식 검사를 다시 실행했다.
- 작업 일지는 내가 프로젝트를 수행하고 학습한 관점으로 작성하고, 표현하지 않은 감정이나 경험은 기록하지 않도록 정했다.
- 내가 다시 사용할 프로젝트 명령에는 목적, 변경 여부, 실행 결과, 성공 기준을 기록하고 필요한 경우 직접 확인 방법도 제공하도록 정했다.

## 회고

기본 디렉터리를 만든 뒤 각각의 용도를 질문해 `설정 -> 코드 실행 -> 로그와 artifact 생성` 흐름을 확인했다. 작업을 진행하면서 기록 시점, 단계별 승인, 한글 주석과 문서, 작업 일지의 관점을 직접 정했다. 앞으로는 한 단계씩 결과를 검수하고 Q&A를 마친 뒤 내 프로젝트 수행 기록으로 위키와 작업 일지를 최종화한다. 프로젝트에서 직접 사용할 명령은 이름만 남기지 않고 왜 실행했으며 무엇이 달라지는지 함께 확인한다.

## 배운 점

- 실행 가능한 코드가 운영 가능한 작업이 되려면 설정, 상태, 로그, artifact, 복구 정보가 함께 필요하다.
- `configs/`와 `src/`는 실행 입력과 동작을 담당하고, `logs/`와 `artifacts/`는 실행 기록과 결과물을 담당한다.
- 로그와 모델 artifact는 크기와 민감 정보 문제 때문에 소스 코드와 다른 Git 정책이 필요하다.
- `.gitkeep`은 빈 디렉터리를 저장소에 표현하기 위한 관례다.
- 목적 중심의 한글 주석과 단계별 검수 기록은 내가 코드의 이유를 이해하고 변경 내용을 확인하는 데 도움을 준다.
- 명령어를 이해하려면 명령 자체뿐 아니라 실행 목적, 상태 변경 여부, 성공 판단 기준을 함께 알아야 한다.
