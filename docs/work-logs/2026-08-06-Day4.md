3. 한 번 더 실행하여 기존 기록 보존, run ID 고유성, field 구조, artifact 연결을 확인하고 README를 갱신했다.
4. 구현 검수와 기술 질문을 마친 뒤 로깅·Linux 운영·MLOps 위키와 Day 4 작업 기록을 최종화했다.

## 코드 및 설정 의도

- `RUN_LOG_PATH`는 현재 학습 실행 이력을 `logs/runs.jsonl` 한 파일에 모으는 기본 경로다.
- `utc_now_iso()`는 환경의 local timezone과 무관하게 실행 시각을 비교할 수 있도록 UTC ISO 8601 문자열을 만든다.
- `append_run_log()`는 한 실행을 JSON 한 줄로 직렬화하고 append mode로 기록하여 기존 이력을 보존한다.
- `log_path.parent.mkdir(parents=True, exist_ok=True)`는 새 환경에서 로그 부모 경로가 없어 저장이 실패하는 상황을 예방한다.
- `ensure_ascii=False`는 한글이 포함되더라도 사람이 읽을 수 있는 형태로 보존한다.
- `run_training_job()`은 run ID 생성, 시각 측정, 학습, artifact 저장, 성공 기록을 하나의 운영 흐름으로 연결한다.
- `perf_counter()`는 시스템 시각 변경의 영향을 받지 않고 실제 경과 시간을 측정하기 위해 사용한다.
- `main()`은 CLI 실행 결과와 파일에 저장한 record를 같은 JSON 구조로 출력한다.

## 실행한 명령과 목적

### `python src/run_job.py`

- 목적: 모델 학습, artifact 저장, 성공 run log 기록을 한 번에 실행한다.
- 변경 여부: `artifacts/{run_id}/model.pkl`을 만들고 `logs/runs.jsonl` 끝에 한 줄을 추가한다.
- 실행 결과: 두 번 모두 exit code 0으로 끝났고 accuracy 약 96.67%, `status`가 `success`인 JSON을 출력했다.
- 성공 기준: 출력과 로그의 run ID 및 artifact 경로가 일치하고, 해당 model 파일이 존재하며, 실행할 때마다 새 로그 줄이 추가된다.

### `tail -n 3 logs/runs.jsonl`

- 목적: 최근 학습 실행 기록을 확인한다.
- 변경 여부: 로그 마지막 세 줄을 읽기만 하며 파일을 변경하지 않는다.
- 실행 결과: 현재 존재하는 두 성공 기록이 서로 다른 run ID와 동일한 field 구조로 출력됐다.
- 성공 기준: 각 줄이 독립된 JSON이며 필요한 field와 실제 artifact 경로를 포함한다.

## 검증 결과

- 임시 경로에 JSONL 두 줄을 추가하고 다시 읽어 각 줄이 정상 JSON임을 확인했다.
- 실제 학습을 두 번 실행해 `logs/runs.jsonl`에 두 줄이 누적됐다.
- 최근 두 기록의 run ID가 서로 다르고 일곱 개 필수 field가 일치했다.
- 각 `artifact_path`에 0 byte보다 큰 model 파일이 존재했다.
- CLI가 출력한 record와 log 마지막 줄이 일치했다.
- 생성된 log와 artifact는 `.gitignore`에 따라 Git 변경 목록에서 제외됐다.
- 구현 및 Markdown 공백 검사에서 오류가 없었다.


첫 번째 명령은 새 model artifact와 run log 한 줄을 생성하고 JSON 결과를 출력한다. 두 번째 명령은 최근 로그를 읽기만 한다. 출력의 `run_id`와 `artifact_path`가 로그 마지막 줄과 일치하고 model 파일이 존재하면 정상이다. 학습 명령을 반복할 때마다 artifact 디렉터리와 로그 줄이 추가된다.

## Codex Q&A

- 질문: `log_path.parent.mkdir(parents=True, exist_ok=True)`는 어떻게 동작하는가?
  답변: `log_path.parent`가 로그 파일의 부모 디렉터리를 선택한다. `parents=True`는 필요한 상위 경로를 함께 만들고, `exist_ok=True`는 디렉터리가 이미 있어도 오류 없이 계속한다. 이후 파일을 append mode로 열어 기존 기록 뒤에 새 줄을 추가한다.
- 질문: Day 3까지는 학습한 model 저장이고 Day 4에는 그 학습의 로그까지 기록하는 것인가?
  답변: 맞다. Day 3의 `model.pkl`은 학습 결과물이고 Day 4의 `runs.jsonl`은 실행 시각, 상태, metric과 artifact 경로를 설명하는 운영 이력이다. 두 결과는 같은 run ID로 연결된다.
- 질문: 현재는 실행 로그 파일 하나에 학습 후 로그를 추가하는 방식인가?
  답변: 맞다. 성공한 모든 실행은 `logs/runs.jsonl` 하나에 JSON 한 줄씩 누적되고 model은 run ID별 디렉터리에 분리된다.

## 발견한 문제

구현과 검증 과정에서 오류는 발견되지 않았다. 다만 현재는 성공한 실행만 기록하며, 상대 경로를 사용하므로 프로젝트 root에서 명령을 실행해야 한다.

## 수정 또는 결정

- 기존 내용을 보존하고 실행별 기록을 추가하기 위해 JSONL과 append mode를 사용했다.
- 실행 시점은 UTC ISO 8601, 경과 시간은 `perf_counter()`로 각각 목적에 맞게 측정했다.
- 모든 성공 run은 하나의 `logs/runs.jsonl`에 누적하고 model artifact는 run ID별 경로로 분리했다.
- Day 4 범위는 성공 로그로 제한하고 실패 상태와 exception 정보는 Day 5에서 추가하기로 했다.

## 회고

Day 3의 model artifact와 Day 4의 run log가 서로 다른 자료라는 점을 구분했다. 실제 결과물은 실행별 디렉터리에 보존하고, 하나의 JSONL에는 그 결과물의 생성 시각과 상태 및 metric을 누적한다. 또한 로그 저장 전에 부모 디렉터리를 준비하는 코드가 새 환경의 경로 누락을 방지한다는 점을 확인했다.

## 배운 점

- structured log는 실행 정보를 일관된 field로 남겨 이후 검색과 비교를 가능하게 한다.
- JSONL은 새 기록을 한 줄씩 추가하므로 운영 이벤트 누적에 적합하다.
- run ID는 로그의 metric과 실제 model artifact를 연결하는 기준이다.
- UTC 시각과 경과 시간 측정용 단조 시계는 서로 다른 목적을 가진다.
- 부모 디렉터리 생성과 append mode는 로그 파일을 안정적으로 누적하기 위한 별도 단계다.
- 상대 경로는 명령을 실행한 현재 작업 디렉터리를 기준으로 해석된다.
