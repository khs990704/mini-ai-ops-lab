# Day 5 - 2026-08-07

## 목표

학습 실패를 안전하게 재현하고 오류 원인과 실행 상태를 structured run log에 남긴 뒤 복구 확인 절차를 문서화한다.

## 완료한 작업

- `src/run_job.py`에 검증용 `--fail` option을 추가했다.
- 학습과 artifact 저장 과정의 일반적인 exception을 `try/except`로 포착했다.
- 실패 record에 오류 종류, 메시지와 traceback을 기록했다.
- 성공과 실패가 동일한 열 개 field를 사용하도록 schema를 맞췄다.
- 성공은 exit code `0`, 실패는 exit code `1`로 process 상태를 구분했다.
- 정상 실행 회귀 검증으로 실패 처리가 기존 학습과 artifact 저장을 깨뜨리지 않음을 확인했다.
- README와 첫 장애 시나리오 문서에 재현, 확인, 복구 절차를 기록했다.

## 단계별 진행과 검수

1. `--fail` option과 제어된 `RuntimeError`를 추가하고, 처리되지 않은 실패가 exit code 1과 raw traceback을 만들며 log·artifact는 추가하지 않음을 확인했다.
2. exception 포착과 failed record 작성을 연결하여 오류 정보가 `logs/runs.jsonl`에 한 줄로 저장되는지 검수했다.
3. 정상 학습을 다시 실행해 success record와 model artifact가 생성되고 failed·success schema가 일치하는지 확인했다.
4. README와 `docs/failure-scenarios.md`에 안전한 재현, exit code, 확인할 log field와 복구 검증 절차를 작성했다.
5. 구현 검수와 기술 질문을 마친 뒤 로깅 위키와 Day 5 작업 기록을 최종화했다.

## 코드 및 설정 의도

- `parse_args()`는 CLI에서 `--fail` 검증 경로를 선택할 수 있게 한다.
- `force_failure=True`는 외부 환경을 손상시키지 않고 항상 같은 `RuntimeError`를 발생시켜 실패 처리를 반복 검증한다.
- `try/except`는 검증용 오류뿐 아니라 `train_model()`과 `save_model()`의 실제 일반 exception도 failed record로 바꾼다.
- failed record는 `metrics`와 `artifact_path`를 `null`로 두고 `error_type`, `error_message`, `traceback`을 채운다.
- success record는 error field를 `null`로 두어 성공과 실패가 동일한 schema를 사용하게 한다.
- `traceback.format_exc()`는 exception이 발생한 호출 경로를 나중에 분석할 수 있도록 문자열로 보존한다.
- 실패 JSON은 `stderr`, 성공 JSON은 `stdout`에 출력하여 상위 process가 결과를 구분하기 쉽게 한다.
- `SystemExit(main())`은 성공 시 0, 실패 시 1을 실제 process exit code로 전달한다.

## 실행한 명령과 목적

### `python src/run_job.py --fail`

- 목적: 의도적인 학습 실패를 발생시켜 exception 처리와 failed log 기록을 확인한다.
- 변경 여부: 최종 구현에서는 `logs/runs.jsonl`에 failed record 한 줄을 추가하고 model artifact는 만들지 않는다.
- 실행 결과: 첫 단계에서는 의도대로 raw traceback과 exit code 1이 발생했지만 failed log가 없었다. exception 처리를 연결한 뒤에는 구조화된 실패 JSON과 failed log가 생성됐고 exit code 1을 유지했다.
- 성공 기준: `status`가 `failed`, 오류 field와 traceback이 존재하고 `metrics`와 `artifact_path`가 `null`이며 process가 exit code 1로 끝난다.

### `tail -n 1 logs/runs.jsonl`

- 목적: 가장 최근 실패 기록의 상태와 오류 원인을 확인한다.
- 변경 여부: 마지막 log 한 줄을 읽기만 한다.
- 실행 결과: `RuntimeError`, 의도한 오류 메시지, traceback과 `failed` 상태가 정상 JSON으로 출력됐다.
- 성공 기준: 한 줄이 독립된 JSON이고 해당 run ID의 실패 정보가 모두 존재한다.

### `python src/run_job.py`

- 목적: 실패 처리 추가 후에도 정상 학습과 artifact 저장이 유지되는지 확인한다.
- 변경 여부: 새 model artifact를 만들고 success record 한 줄을 추가한다.
- 실행 결과: exit code 0, accuracy 약 96.67%, 실제 model 경로와 `success` 상태가 출력됐다.
- 성공 기준: error field는 `null`, metric과 artifact 경로는 존재하고 해당 model 파일이 실제로 생성된다.

### `tail -n 2 logs/runs.jsonl`

- 목적: 최근 failed와 success 기록을 나란히 비교한다.
- 변경 여부: 최근 두 log를 읽기만 한다.
- 실행 결과: 두 record의 status와 값은 다르지만 열 개 field 구조와 run ID 고유성이 유지됐다.
- 성공 기준: `failed` 뒤에 `success`가 있고 각각 오류 정보와 실행 결과가 상태에 맞게 채워진다.

### `python src/run_job.py --help`

- 목적: 사용 가능한 CLI option과 `--fail`의 검증 목적을 확인한다.
- 변경 여부: 도움말만 출력하며 log와 artifact를 만들지 않는다.
- 실행 결과: `--fail` 설명이 한글로 출력되고 exit code 0으로 끝났다.
- 성공 기준: option 이름과 설명이 표시되고 실행 결과물이 추가되지 않는다.

## 검증 결과

- 제어된 `RuntimeError`가 반복 가능하게 발생했다.
- failed record에 run ID, 상태, 시각, 실행 시간, 오류 종류·메시지와 traceback이 저장됐다.
- 실패 실행은 model artifact를 만들지 않고 exit code 1을 반환했다.
- 정상 실행은 model artifact와 success record를 만들고 exit code 0을 반환했다.
- 최근 failed·success record가 동일한 열 개 field와 서로 다른 run ID를 사용했다.
- success record의 artifact 경로에 실제 model 파일이 존재했다.
- JSONL traceback은 줄바꿈이 escape되어 한 실행이 한 물리적 줄을 유지했다.
- README 링크, 장애 문서와 Git 형식 검사에서 오류가 없었다.

## Codex Q&A

- 질문: `run_training_job()`에 `force_failure=True`를 보내면 임시 실패 환경이 테스트되는 것인가?
  답변: 제어된 `RuntimeError`를 발생시켜 실패 경로를 테스트하는 것은 맞지만 실제 인프라 장애를 만드는 것은 아니다. CLI의 `--fail`이 같은 값을 전달하며 학습과 artifact 저장 전에 오류를 발생시킨다.
- 질문: 실패할 때 failed log가 남는지 테스트하기 위해 수정하고 테스트한 것인가?
  답변: 맞다. `--fail`은 반복 가능한 검증 장치이고, `try/except`와 failed record 작성은 이후 실제 학습·저장 exception에도 적용되는 운영 기능이다.

## 발견한 문제

첫 번째 제어 실패에서는 exception을 아직 포착하지 않아 raw traceback만 terminal에 나타났고 실패 run은 기록되지 않았다. 이 상태는 실패 후 원인을 나중에 추적할 수 없다는 운영상 공백을 보여줬다.

## 수정 또는 결정

- 일반적인 작업 exception을 포착하고 failed record를 남기도록 실행 경계를 `try/except`로 감쌌다.
- exception을 기록하더라도 process 실패가 숨겨지지 않도록 exit code 1을 유지했다.
- 검증용 실패는 학습 전에 발생시켜 불필요한 artifact나 부분 결과를 만들지 않게 했다.
- success와 failed record가 같은 field를 사용하도록 상태에 해당하지 않는 값은 `null`로 기록했다.
- `KeyboardInterrupt`와 `SystemExit` 같은 process 제어 신호는 `except Exception`으로 변환하지 않기로 했다.

## 회고

제어된 실패를 먼저 발생시켜 terminal의 raw traceback만으로는 실행 이력이 남지 않는다는 차이를 확인했다. 이후 같은 오류를 structured failed record로 보존하면서도 exit code 1을 유지해, 오류 기록과 상위 process의 실패 감지를 함께 만족시켰다. 검증용 오류 발생 장치와 실제 exception 처리 기능의 역할도 구분했다.

## 배운 점

- 재현 가능한 실패 조건이 있어야 실패 처리도 반복해서 검증할 수 있다.
- exception을 포착하는 것과 실패를 성공으로 처리하는 것은 다르며 non-zero exit code를 유지해야 한다.
- 오류 종류와 메시지는 현상을 요약하고 traceback은 발생 위치와 호출 경로를 보여준다.
- success와 failed record의 공통 schema는 상태별 실행을 비교하기 쉽게 한다.
- `stdout`, `stderr`, exit code는 CLI 실행 결과를 상위 시스템에 전달하는 서로 다른 통로다.
- 복구 확인은 원인을 제거한 뒤 정상 실행과 success log 및 artifact 생성까지 검증해야 한다.
