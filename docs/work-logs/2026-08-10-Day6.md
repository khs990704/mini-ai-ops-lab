## 코드 및 설정 의도

- `FROM python:3.12-slim`은 local Python과 분리된 가벼운 Python 3.12 실행 기준을 만든다.
- `PYTHONDONTWRITEBYTECODE=1`은 실행 image 안의 불필요한 Python cache 생성을 줄인다.
- `PYTHONUNBUFFERED=1`은 학습 결과와 오류가 terminal에 지연 없이 출력되게 한다.
- `requirements.txt`를 source보다 먼저 복사해 source만 변경될 때 dependency 설치 layer cache를 재사용한다.
- `appuser`는 실제 container 작업을 root가 아닌 제한된 사용자로 실행한다.
- `CMD`는 별도 명령이 없을 때 기존 `src/run_job.py`를 자동 실행한다.
- `.dockerignore`는 Git 정보, virtual environment, cache, 기존 실행 결과, `.env`와 문서를 build context에서 제외한다.
- Bind mount는 container를 제거해도 host의 log와 artifact를 보존한다.
- `--user`는 bind mount에 생성되는 파일을 현재 WSL 계정으로 계속 관리할 수 있게 한다.
- `--rm`은 일회성 batch job이 끝난 뒤 실행 container만 제거하며 image와 host 결과는 유지한다.

## 실행한 명령과 목적

### `docker build -t mini-ai-ops-lab:day6 .`

- 목적: Dockerfile과 현재 source로 실행 image를 만든다.
- 변경 여부: base image와 package를 내려받고 local Docker image 및 build cache를 생성한다.
- 실행 결과: exit code 0으로 `mini-ai-ops-lab:day6` image가 생성됐고 build context는 약 14.47kB였다.
- 성공 기준: 모든 build layer가 완료되고 지정한 image tag가 생성된다.

### `docker run --rm --user 1000:1000 --mount type=bind,source=/home/hskim/project/mini-ai-ops-lab/logs,target=/app/logs --mount type=bind,source=/home/hskim/project/mini-ai-ops-lab/artifacts,target=/app/artifacts mini-ai-ops-lab:day6`

- 목적: Container dependency로 정상 학습을 실행하고 결과를 host에 보존한다.
- 변경 여부: host의 `logs/runs.jsonl`에 success record를 추가하고 새 model artifact를 만든다. 종료된 container는 자동 제거한다.
- 실행 결과: exit code 0, accuracy 약 96.67%, success JSON과 824-byte `model.pkl`이 생성됐다.
- 성공 기준: host log와 artifact가 같은 run ID로 연결되고 파일 소유권이 `1000:1000`이다.

### `docker run --rm --user 1000:1000 --mount type=bind,source=/home/hskim/project/mini-ai-ops-lab/logs,target=/app/logs --mount type=bind,source=/home/hskim/project/mini-ai-ops-lab/artifacts,target=/app/artifacts mini-ai-ops-lab:day6 python src/run_job.py --fail`

- 목적: 동일한 container 환경에서 제어 실패와 failed log 기록을 확인한다.
- 변경 여부: host run log에 failed record만 추가하고 model artifact는 만들지 않는다. 종료된 container는 자동 제거한다.
- 실행 결과: 예상된 exit code 1, `RuntimeError`, 오류 메시지와 `/app/src/run_job.py` traceback이 기록됐다.
- 성공 기준: `status`가 `failed`, 오류 field가 존재하고 metric과 artifact 경로가 `null`이다.

### `tail -n 2 logs/runs.jsonl`

- 목적: Container가 host에 남긴 최근 success·failed record를 확인한다.
- 변경 여부: 최근 두 log를 읽기만 한다.
- 실행 결과: container run ID를 가진 success와 failed JSON이 순서대로 출력됐다.
- 성공 기준: 상태별 field가 올바르고 success artifact 경로에 실제 model 파일이 존재한다.

## 검증 결과

- Docker 29.3.1과 Docker Compose v5.1.1 환경에서 image build가 성공했다.
- Image의 기본 사용자는 `appuser`, 기본 명령은 `python src/run_job.py`였다.
- 정상 container는 exit code 0, success log와 model artifact를 생성했다.
- 실패 container는 exit code 1, failed log를 생성하고 artifact는 만들지 않았다.
- Host run log는 4줄에서 6줄로 늘어 정확히 두 실행이 추가됐다.
- Bind mount 결과 파일의 UID·GID가 현재 WSL 사용자인 `1000:1000`이었다.
- `--rm` 실행 후 해당 image를 사용한 종료 container가 남지 않았다.
- Local 실행과 container 실행의 accuracy는 같았다.
- Host의 scikit-learn 1.5.1과 container의 1.9.0 차이로 pickle 크기가 834바이트와 824바이트로 달랐다.
- README와 Docker 설정의 Git 형식 검사에서 오류가 없었다.

## 직접 확인 방법

Docker daemon이 실행 중인 WSL 환경에서 프로젝트 root로 이동한다.

```bash
cd /home/hskim/project/mini-ai-ops-lab
docker build -t mini-ai-ops-lab:day6 .
docker run --rm \
  --user "$(id -u):$(id -g)" \
  --mount type=bind,source="$PWD/logs",target=/app/logs \
  --mount type=bind,source="$PWD/artifacts",target=/app/artifacts \
  mini-ai-ops-lab:day6
tail -n 1 logs/runs.jsonl
```

Build는 image와 cache를 만들고 package를 내려받을 수 있다. Container 실행은 host에 success log와 model artifact를 만들며 container만 자동 제거한다. 마지막 명령은 최근 log를 읽기만 한다. Source나 dependency가 변경되면 image를 다시 build해야 최신 내용이 반영된다.

## Codex Q&A

- 질문: Docker container를 만드는 목적은 무엇인가?
  답변: 현재 WSL에 우연히 설치된 환경에 의존하지 않고 Python, dependency와 실행 방법을 묶어 다른 환경에서도 같은 코드를 실행하기 위해서다.
- 질문: 실제로 어떻게 사용하는가?
  답변: 처음 또는 source 변경 후 `docker build`로 image를 만들고, `docker run`으로 container를 실행한다. 보존할 log와 artifact는 bind mount로 host에 연결한다.
- 질문: Day 5까지의 기능을 Docker 기반으로 수정한 것인가?
  답변: 아니다. 기존 `src/`는 그대로 두고 같은 코드를 실행하는 별도 Docker 환경을 추가했다. Local Python 방식도 계속 사용할 수 있다.
- 질문: `requirements.txt` 같은 실행환경만 Docker로 만든 것인가?
  답변: 실행환경이라는 이해는 맞으며, image에는 Linux 기반 환경과 Python, dependency뿐 아니라 `src/` 코드, 결과 경로와 기본 명령도 포함된다.
- 질문: 실행할 때도 Python 명령을 사용하는가?
  답변: WSL에서는 `docker run`을 사용한다. 별도 명령이 없으면 Dockerfile의 `CMD`가 container 안에서 `python src/run_job.py`를 실행하고, image 이름 뒤에 다른 명령을 적으면 기본값을 덮어쓴다.
- 질문: 왜 `--rm`을 사용하는가?
  답변: 한 번 실행하고 끝나는 학습 container가 쌓이지 않게 자동 제거하기 위해서다. Image와 bind mount 결과는 삭제하지 않는다.
- 질문: 매번 `--rm`을 쓰는 방법밖에 없는가?
  답변: 이름 있는 container 재사용, 장기 실행 개발 container와 Docker Compose도 가능하다. 현재는 깨끗한 실행 상태와 결과 보존이 중요한 batch job이므로 새 container와 `--rm` 조합을 선택했다.

## 발견한 문제

기능 오류는 없었지만 host와 container가 `requirements.txt` 범위 안에서 서로 다른 dependency version을 선택했다. Metric은 같았으나 pickle 직렬화 크기가 달라, 호환 가능한 version 범위와 완전히 고정된 재현 환경은 다르다는 점이 확인됐다.

Image build 중 `pip`가 root 설치 경고를 출력했다. Package를 image system 영역에 설치하는 build layer에서 발생한 경고이며, 완성 image의 기본 실행 계정이 `appuser`임을 metadata로 확인해 실제 작업은 non-root로 실행되도록 구분했다.

## 수정 또는 결정

- 기존 Python 코드를 Docker 전용으로 변경하지 않고 실행환경만 추가했다.
- 결과 보존이 필요한 실행은 `logs/`와 `artifacts/`만 bind mount하기로 했다.
- Host에 root 소유 파일을 만들지 않도록 현재 WSL UID·GID로 container를 실행했다.
- 학습 작업은 일회성 batch job이므로 image는 재사용하고 container는 실행마다 새로 만들어 자동 제거하기로 했다.
- 현재는 호환 가능한 dependency 범위를 유지하고, 완전한 rebuild 재현이 필요할 때 lock file이나 정확한 version 고정을 추가하기로 했다.
- Pickle model은 가능한 한 생성한 image 환경에서 불러오기로 했다.

## 회고

기존 기능을 Docker 기반 코드로 바꾸는 것과 기존 코드를 Docker 환경에서 실행하는 것은 다르다는 점을 구분했다. Image는 재사용할 실행환경이고 container는 한 번의 학습 실행이며, 보존 대상은 container 자체가 아니라 run log와 model artifact라는 기준으로 `--rm`과 bind mount 조합을 선택했다. Dependency 범위가 호환성을 제공하지만 동일한 rebuild까지 보장하지 않는다는 점도 실제 artifact 차이로 확인했다.

## 배운 점

- Docker image는 실행환경, dependency, 코드와 기본 명령을 함께 묶는다.
- Container는 image의 실행 인스턴스이며 batch job마다 새로 만들 수 있다.
- Bind mount는 일시적인 container와 보존할 운영 결과를 분리한다.
- `--rm`은 container만 제거하고 image와 host bind mount 결과는 유지한다.
- Non-root 실행과 host UID·GID 전달은 권한 및 파일 소유권 문제를 줄인다.
- Image layer 순서는 rebuild cache 효율에 영향을 준다.
- Version 범위와 lock file은 서로 다른 재현성 수준을 제공한다.
- Source가 바뀌어도 기존 image는 자동 갱신되지 않으므로 다시 build해야 한다.
