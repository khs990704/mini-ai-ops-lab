## 코드 및 설정 의도

- `docs/architecture.md`는 날짜별 진행 이력이 아니라 현재 시스템의 구성요소 책임, 실행 sequence, 데이터 연결과 운영 경계를 설명한다.
- 현재 구현 범위를 먼저 명시하여 config, Agent, audit log처럼 아직 없는 기능을 architecture에 섞지 않는다.
- 구성요소 표의 `하지 않는 일`은 책임 경계를 보여주고 한 파일이 모든 역할을 가진 것처럼 이해하는 것을 방지한다.
- 성공과 실패 sequence를 분리해 공통 schema와 상태별 값 및 exit code 차이를 설명한다.
- 현재 제약은 완료되지 않은 기능을 숨기지 않고 이후 확장의 기준으로 사용한다.
- README는 빠른 전체 이해와 실행 방법을 제공하고, 상세 설계는 architecture 문서로 연결한다.
- `docs/work-logs/`는 날짜별 작업·검수 이력, architecture는 현재 시스템 구조라는 문서 책임을 분리한다.

## 실행한 명령과 목적

### `python src/run_job.py`

- 목적: 첫 주의 정상 학습, model 저장과 success log 전체 흐름을 회귀 검증한다.
- 변경 여부: 새 run ID의 `model.pkl`과 success record 한 줄을 생성한다.
- 실행 결과: exit code 0, accuracy 약 96.67%, 834-byte model artifact가 생성됐다.
- 성공 기준: JSON의 run ID와 artifact 경로가 일치하고 실제 model 파일 및 success log가 존재한다.

### `python src/run_job.py --fail`

- 목적: 제어된 실패와 failed log 및 process 상태를 회귀 검증한다.
- 변경 여부: failed record 한 줄을 추가하지만 model artifact는 만들지 않는다.
- 실행 결과: 예상된 exit code 1, `RuntimeError`, 오류 메시지와 traceback이 기록됐다.
- 성공 기준: error field가 존재하고 `metrics`와 `artifact_path`는 `null`이며 실패 exit code를 유지한다.

### `tail -n 2 logs/runs.jsonl`

- 목적: 방금 생성한 success와 failed record를 나란히 확인한다.
- 변경 여부: 최근 두 log를 읽기만 한다.
- 실행 결과: 서로 다른 run ID의 success·failed JSON이 공통 열 개 field를 사용했다.
- 성공 기준: 상태별 값이 올바르고 success record의 artifact 파일만 실제로 존재한다.

## 검증 결과

- Architecture가 참조하는 코드, 결과 경로와 관련 문서가 모두 존재했다.
- 문서의 구성요소 책임과 성공·실패 흐름이 현재 코드와 일치했다.
- README에서 현재 구현과 향후 config·Agent 기능이 명확히 구분됐다.
- 정상 실행은 exit code 0, success log와 834-byte model을 생성했다.
- 실패 실행은 exit code 1, failed log와 traceback을 생성하고 artifact는 만들지 않았다.
- 최근 두 record의 schema가 동일하고 run ID는 서로 달랐다.
- 생성 log와 artifact는 Git 변경 목록에서 제외됐다.
- 문서 링크, Markdown 공백과 Git 형식 검사에서 오류가 없었다.

- README의 architecture를 현재 `run_job.py`, `train_job.py`, `storage.py`, log와 artifact 흐름으로 교체했다.
- Config, Agent tool runner, audit log와 추가 운영 문서는 향후 구현으로 명시했다.
- Architecture에는 현재 제약과 미구현 범위를 숨기지 않고 기록했다.
- Day 7에는 새 기능을 추가하지 않고 문서 기준선과 기존 기능 회귀 검증에 집중했다.

## 회고

Day 1~6의 기능을 날짜별 결과로만 두지 않고 현재 실행 흐름과 구성요소 책임으로 다시 연결했다. README는 빠른 이해와 실행 안내, architecture는 상세 구조와 운영 경계, 작업 일지는 날짜별 과정과 검수 이력을 담당하도록 문서 역할을 구분했다. 구현된 기능과 계획 중인 기능을 분리해 현재 프로젝트 상태를 과장하지 않는 기준선도 만들었다.

## 배운 점

- Architecture 문서는 파일 목록보다 구성요소의 책임과 상호작용을 설명해야 한다.
- `run_job.py`는 orchestration, `train_job.py`는 학습, `storage.py`는 artifact 책임을 가진다.
- Run ID는 실행 log와 model artifact 사이의 추적 기준이다.
- 현재 제약을 기록하면 이후 확장의 필요성과 순서를 판단하기 쉽다.
- README, architecture, 작업 일지는 서로 다른 독자와 목적을 가진다.
- 문서 정리 후에도 실제 success·failed 경로를 실행해 설명과 동작이 일치하는지 확인해야 한다.
