# Day 8 - 2026-08-11

## 목표

학습 조건을 Python source의 고정값에서 YAML 설정으로 분리하고, 검증된 실제 설정을 학습과 run log 및 Docker 실행에 일관되게 연결한다.

## 완료한 작업

- `configs/train.yaml`에 `test_size`, `random_state`, `max_iterations`를 정의했다.
- `src/config_loader.py`에서 YAML 읽기와 필수·추가 항목, 자료형 및 값 범위 검증을 구현했다.
- `src/train_job.py`가 고정 상수 대신 검증된 설정으로 data를 분리하고 model을 학습하도록 변경했다.
- `train_job.py`와 `run_job.py`에 `--config` option을 추가했다.
- 성공·실패 run record에 `config_path`와 실제 `config`를 기록했다.
- 설정 파일 누락을 model 생성 전 실패로 처리하고 `FileNotFoundError`를 JSONL에 남겼다.
- Docker image에 `configs/`를 포함하고 container에서도 설정 기반 학습을 검증했다.
- README와 architecture를 Day 8의 현재 실행 구조에 맞게 갱신했다.

## 단계별 진행과 검수

1. `configs/train.yaml`과 설정 로더를 만들고 정상 설정 및 범위 오류를 검증했다.
2. `train_job.py`에 설정을 전달하여 직접 학습, metric 출력과 model 저장을 확인했다.
3. `run_job.py`에 설정 경로를 연결하고 success record와 설정 파일 누락 failed record를 확인했다.
4. Dockerfile에 설정 디렉터리를 포함하고 새 image의 host log·artifact 생성을 확인했다.
5. README와 architecture에 설정 항목, 실행 명령, 구성요소 책임과 성공·실패 흐름을 반영했다.
6. 구현과 질문 검수 후 MLOps·로깅 위키 및 Day 8 작업 기록을 최종화했다.

## 코드 및 설정 의도

- `configs/train.yaml`은 Python 코드를 수정하지 않고 실험 조건을 바꾸기 위한 기본 설정 파일이다.
- `TrainConfig`는 검증 후 학습 코드가 기대할 설정 구조를 명시한다.
- `load_train_config()`는 잘못된 실험 조건이 학습까지 전달되지 않도록 실행 경계에서 YAML 구조와 값을 검사한다.
- 알 수 없는 설정 항목도 거부하여 오타가 조용히 무시되는 상황을 막는다.
- Python의 `bool`이 `int`로도 판정되는 특성을 고려해 정수 설정에서 `true`, `false`를 명시적으로 제외한다.
- `train_model()`은 전달받은 설정을 사용하되 기존 호출 경로에도 기본 설정을 적용해 중간 단계의 호환성을 유지한다.
- `run_training_job()`은 설정 로드부터 하나의 run으로 취급하여 학습 전 오류도 같은 JSONL 실패 schema에 기록한다.
- `config_path`는 요청한 파일을, `config`는 검증을 통과해 실제 사용한 값을 나타낸다. 파일 자체를 읽지 못하면 `config`는 `null`이다.
- Dockerfile의 `COPY configs/ ./configs/`는 local과 container가 같은 기본 학습 조건을 사용하게 한다.
- 중요한 모듈·함수·판단의 목적은 이해하기 쉬운 짧은 한글 주석과 docstring으로 남겼다.

## 실행한 명령과 목적

아래 명령은 Day 8 구현 검증을 위해 Codex가 프로젝트 root에서 실행했다. 사용자가 별도로 실행한 것으로 기록하지 않는다.

### `python -c "from src.config_loader import load_train_config; print(load_train_config('configs/train.yaml'))"`

- 목적: 기본 YAML이 검증을 통과하고 학습에 전달할 dict로 반환되는지 확인한다.
- 변경 여부: 설정을 읽기만 하며 project 파일을 변경하지 않는다.
- 실행 결과: exit code 0과 `test_size: 0.2`, `random_state: 42`, `max_iterations: 200`이 출력됐다.
- 성공 기준: 세 값이 올바른 자료형과 값으로 출력된다.

### 잘못된 `test_size: 2`를 표준입력으로 전달한 설정 검증

- 목적: 허용 범위를 벗어난 설정이 학습 전에 거부되는지 확인한다.
- 변경 여부: 임시 표준입력만 읽고 project 파일을 변경하지 않는다.
- 실행 결과: 예상된 exit code 1과 `ValueError: test_size는 0보다 크고 1보다 작아야 합니다.`가 출력됐다.
- 성공 기준: 잘못된 값을 반환하지 않고 명확한 오류로 중단한다.

### `python src/train_job.py --config configs/train.yaml`

- 목적: 검증된 설정이 실제 data 분리와 model 학습에 적용되는지 직접 확인한다.
- 변경 여부: `artifacts/{run_id}/model.pkl`을 생성하지만 run log는 추가하지 않는다.
- 실행 결과: exit code 0, accuracy 약 96.67%, 학습 120개·검증 30개와 적용 설정이 출력됐고 model이 생성됐다.
- 성공 기준: 출력의 `config_path`, `config`, metric과 실제 artifact 경로가 일치한다.

### `python src/run_job.py --config configs/train.yaml`

- 목적: 설정 로드, 학습, artifact 저장과 success log를 연결한 운영 흐름을 검증한다.
- 변경 여부: 새 model artifact와 `logs/runs.jsonl`의 success record 한 줄을 생성한다.
- 실행 결과: exit code 0, accuracy 약 96.67%, `config_path`와 세 설정값이 포함된 success record가 저장됐다.
- 성공 기준: record의 run ID와 model 경로가 일치하고 실제 사용 설정이 함께 기록된다.

### `python src/run_job.py --config configs/missing.yaml`

- 목적: 설정 파일 누락이 model 학습 전 실패로 기록되는지 확인한다.
- 변경 여부: failed record 한 줄을 추가하고 model artifact는 만들지 않는다.
- 실행 결과: 예상된 exit code 1, `FileNotFoundError`, 요청 경로와 `config: null`이 기록됐다.
- 성공 기준: 실패 원인과 경로가 JSONL에 남고 해당 run의 model 디렉터리는 생성되지 않는다.

### `docker build -t mini-ai-ops-lab:day8 .`

- 목적: source, dependency와 기본 학습 설정을 포함한 Day 8 Docker image를 만든다.
- 변경 여부: local Docker image와 build cache를 생성하거나 갱신한다. 기존 `day6` image는 유지한다.
- 실행 결과: exit code 0으로 `mini-ai-ops-lab:day8` image를 만들었고 `COPY configs/ ./configs/` 단계를 확인했다.
- 성공 기준: build가 완료되고 새 image tag가 생성된다.

### Day 8 Docker image 실행

```bash
docker run --rm \
  --user "$(id -u):$(id -g)" \
  --mount type=bind,source="$PWD/logs",target=/app/logs \
  --mount type=bind,source="$PWD/artifacts",target=/app/artifacts \
  mini-ai-ops-lab:day8
```

- 목적: container 내부의 기본 설정으로 학습하고 결과를 host에 보존한다.
- 변경 여부: host의 `logs/`와 `artifacts/`에 success record와 model을 생성하고 종료된 container는 `--rm`으로 제거한다. image는 유지한다.
- 실행 결과: exit code 0, accuracy 약 96.67%, 설정값이 포함된 success log와 model이 생성됐고 파일 소유자는 WSL 사용자와 일치했다.
- 성공 기준: host에서 새 JSONL record와 `artifacts/{run_id}/model.pkl`을 확인할 수 있다.

### `python src/run_job.py --help`

- 목적: README에 적은 `--config`와 `--fail` option이 실제 CLI와 일치하는지 확인한다.
- 변경 여부: 도움말을 출력할 뿐 파일을 변경하지 않는다.
- 실행 결과: exit code 0과 `--config CONFIG`, 기본값 `configs/train.yaml`이 출력됐다.
- 성공 기준: 문서에 안내한 option과 기본 경로가 도움말에 존재한다.

## 검증 결과

- 정상 YAML은 검증된 세 설정값으로 반환됐다.
- 잘못된 `test_size`는 학습 전에 `ValueError`로 거부됐다.
- Local 직접 학습과 운영 실행 모두 같은 설정으로 accuracy 약 96.67%를 만들었다.
- 정상 운영 run은 model, metric, 설정 경로와 실제 설정값을 하나의 record로 연결했다.
- 누락된 설정 파일은 exit code 1과 failed record를 남겼고 artifact를 생성하지 않았다.
- Docker image에 `configs/train.yaml`이 포함됐고 container run도 host에 정상 결과를 보존했다.
- Docker가 생성한 log와 model의 소유권은 현재 WSL 사용자와 일치했다.
- CLI 도움말, README와 architecture의 실행 설명이 실제 동작과 일치했다.
- Markdown 공백 및 Git diff 형식 검사에서 오류가 없었다.

## 직접 확인 방법

검증은 이미 완료됐으므로 반복 실행은 필수가 아니다. 직접 확인하려면 dependency가 준비된 WSL에서 프로젝트 root로 이동한다.

```bash
cd /home/hskim/project/mini-ai-ops-lab
python src/run_job.py --config configs/train.yaml
tail -n 1 logs/runs.jsonl
```

첫 번째 명령은 새 model과 success log를 생성한다. 두 번째 명령은 파일을 변경하지 않고 방금 기록한 JSON 한 줄을 보여준다. `status: "success"`, `config_path: "configs/train.yaml"`, 실제 `config`와 존재하는 `artifact_path`가 있으면 성공이다.

## Codex Q&A

- 질문: `config_loader.py`에서는 `train.yaml`의 config 값을 불러오되 조건에 맞는지도 확인하는가?
  답변: 맞다. YAML을 읽고 필수·추가 항목, 자료형과 값 범위를 검사한다. 모두 통과한 설정만 반환하며 잘못된 값은 학습 전에 `ValueError`로 중단한다.

## 발견한 문제

- 기존 Dockerfile은 `src/`만 image에 복사하므로 설정 기반 학습으로 바뀐 뒤 `configs/train.yaml`을 container에서 찾을 수 없는 구조였다.
- 기능 검증에서 잘못된 범위와 존재하지 않는 경로를 의도적으로 사용했으며, 두 경우 모두 계획한 실패 처리로 동작했다. 별도의 미해결 기능 오류는 없었다.

## 수정 또는 결정

- 기본 학습값을 source 상수가 아니라 `configs/train.yaml`에서 관리한다.
- 설정 로더가 필수 항목뿐 아니라 추가 항목과 값 범위도 엄격하게 검사하도록 했다.
- run log에는 경로만 남기지 않고 검증된 실제 설정값을 함께 저장하기로 했다.
- 설정을 읽지 못한 실패도 run ID, 오류와 요청 경로를 남기고 process exit code 1을 유지한다.
- Dockerfile에 `configs/` 복사를 추가하고 Day 8 tag로 새 image를 빌드해 기존 image를 보존했다.

## 회고

이번 작업에서는 설정 파일을 읽는 것과 설정이 유효한지 검사하는 것이 별개의 동작임을 코드 경계로 확인했다. 사용자의 질문을 기준으로 `config_loader.py`가 두 책임을 함께 수행하되, 검증된 설정만 학습 코드에 전달한다는 점을 문서와 위키에 명확히 남겼다. 또한 설정을 외부화하면 local 실행뿐 아니라 Docker image가 그 파일을 포함하는지도 함께 점검해야 한다는 운영 기준을 확인했다.

## 배운 점

- 설정 외부화는 source 수정 없이 실험 조건을 바꾸기 위한 기반이다.
- YAML 형식만 사용해서는 안전하지 않으며 실행 전에 항목, 자료형과 값 범위를 검증해야 한다.
- 같은 `random_state`와 설정값은 동일한 data 분리와 결과 재현에 도움을 준다.
- Run log에는 설정 경로와 실제 사용값을 함께 기록해야 나중에 실행 조건을 추적하기 쉽다.
- 설정 파일을 읽지 못했다면 `config: null`로 검증된 값이 없다는 사실을 표현할 수 있다.
- Docker 실행에 필요한 설정 파일도 source와 함께 image에 포함해야 한다.
