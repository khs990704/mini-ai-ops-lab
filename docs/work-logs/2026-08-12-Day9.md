- Local과 Docker에서 experiment tracking 학습과 최근 run 조회를 검증했다.
- README와 architecture에 experiment, run ID, model artifact의 연결 구조를 반영했다.

6. 구현과 사용자 질문 검수 후 MLOps·로깅 위키 및 Day 9 작업 기록을 최종화했다.

## 코드 및 설정 의도

- `experiment_name`은 같은 목적의 여러 run을 묶는 label이며, 개별 실행을 유일하게 식별하는 `run_id`와 역할이 다르다.
- `config_loader.py`는 이름 없는 run이 쌓이지 않도록 비어 있지 않은 문자열을 요구하고 앞뒤 공백을 제거하며 길이를 100자로 제한한다.
- `config`는 검증된 설정 전체를 보존하고, 최상위 `experiment_name`과 `parameters`는 비교 도구가 중첩 구조를 반복 해석하지 않게 한다.
- `TRAINING_PARAMETER_KEYS`는 experiment 이름을 학습값과 분리하고 비교 대상 parameter를 한곳에서 정한다.
- 설정 검증 후 실패하면 experiment와 parameter를 failed record에도 남겨 실패 조건을 추적한다. 설정 자체를 읽지 못했다면 해당 field는 `null`이다.
- `list_runs.py`는 JSONL을 수정하지 않고 filter를 통과한 최근 N개만 `deque`에 보관해 log 크기보다 조회 개수에 맞춰 memory를 사용한다.
- 과거 record는 없는 값을 `-`로 표시하고 기존 `config`의 학습값으로 parameter 열을 보완하되 원본을 변경하지 않는다.
- 손상된 JSON line 하나 때문에 전체 운영 기록 조회가 중단되지 않도록 warning 후 해당 line만 건너뛴다.
- 조회 결과는 shell에서 비교하거나 복사하기 쉬운 tab 구분 열로 출력한다.
- 중요한 함수와 호환 처리에는 동작을 반복 설명하지 않고 운영 목적을 나타내는 짧은 한글 docstring과 주석을 사용했다.

## 실행한 명령과 목적

아래 명령은 Day 9 구현 검증을 위해 Codex가 프로젝트 root에서 실행했다. 사용자가 별도로 실행한 것으로 기록하지 않는다.

### `python -c "from src.config_loader import load_train_config; print(load_train_config('configs/train.yaml'))"`

- 목적: 기본 설정이 새 experiment 이름과 기존 학습값을 모두 반환하는지 확인한다.
- 변경 여부: 설정을 읽기만 하며 log와 artifact를 만들지 않는다.
- 실행 결과: exit code 0과 `experiment_name: iris-baseline` 및 세 parameter가 출력됐다.
- 성공 기준: 이름과 학습값이 검증된 `TrainConfig`로 반환된다.

### 공백뿐인 experiment 이름 검증

```bash
printf 'experiment_name: "   "\ntest_size: 0.2\nrandom_state: 42\nmax_iterations: 200\n' \
  | python -c "from src.config_loader import load_train_config; load_train_config('/dev/stdin')"
```

- 목적: 식별할 수 없는 experiment 이름을 학습 전에 거부하는지 확인한다.
- 변경 여부: 표준입력만 읽고 project 파일을 변경하지 않는다.
- 실행 결과: 예상된 exit code 1과 `ValueError: experiment_name은 비어 있지 않은 문자열이어야 합니다.`가 출력됐다.
- 성공 기준: 잘못된 설정을 반환하지 않고 명확한 오류로 중단한다.

### `python src/run_job.py --config configs/train.yaml`

- 목적: experiment 이름, parameter, metric과 artifact를 success record 하나로 연결한다.
- 변경 여부: 새 model과 `logs/runs.jsonl`의 success record 한 줄을 생성한다.
- 실행 결과: exit code 0, accuracy 약 96.67%와 `iris-baseline`이 기록됐고 `artifacts/20260812T003313853388Z-076af5dc/model.pkl`이 생성됐다.
- 성공 기준: 동일 record에 `experiment_name`, `parameters`, `metrics`와 실제 `artifact_path`가 존재한다.

### `python src/run_job.py --config configs/train.yaml --fail`

- 목적: 검증된 experiment와 parameter가 제어 실패 record에도 보존되는지 확인한다.
- 변경 여부: failed record 한 줄을 추가하고 model은 만들지 않는다.
- 실행 결과: 예상된 exit code 1, `RuntimeError`, `iris-baseline`과 세 parameter가 기록됐고 metric과 artifact 경로는 `null`이었다.
- 성공 기준: 실패 조건을 추적할 정보는 유지하면서 실패 run의 model은 생성하지 않는다.

### `python src/list_runs.py --limit 5`

- 목적: 전체 최근 run을 최신순으로 비교하고 과거 schema 호환을 확인한다.
- 변경 여부: `logs/runs.jsonl`을 읽기만 한다.
- 실행 결과: exit code 0으로 Day 9 success·failed record와 Day 8 record가 함께 출력됐다. 과거 experiment 이름은 `-`, 기존 config의 parameter는 비교 열에 표시됐다.
- 성공 기준: 최신순, 최대 5개와 비교 field가 표시되고 과거 record 때문에 중단되지 않는다.

### `python src/list_runs.py --experiment iris-baseline --limit 3`

- 목적: 지정한 experiment에 속한 최근 run만 조회한다.
- 변경 여부: log를 읽기만 한다.
- 실행 결과: exit code 0으로 `iris-baseline`의 success·failed run만 출력됐다.
- 성공 기준: 다른 experiment와 이름 없는 과거 record가 제외된다.

### `python src/list_runs.py --limit 0`

- 목적: 유효하지 않은 조회 개수가 실행 전에 거부되는지 확인한다.
- 변경 여부: argument 검증에서 종료되므로 log를 읽거나 변경하지 않는다.
- 실행 결과: 예상된 exit code 2와 `limit은 1 이상의 정수여야 합니다.`가 출력됐다.
- 성공 기준: 1 미만의 limit으로 조회를 시작하지 않는다.

### `docker build -t mini-ai-ops-lab:day9 .`

- 목적: experiment tracking source와 설정을 포함한 Day 9 image를 만든다.
- 변경 여부: local Docker image와 build cache를 생성하거나 갱신하며 이전 image는 유지한다.
- 실행 결과: exit code 0으로 `mini-ai-ops-lab:day9` image가 생성됐다.
- 성공 기준: `src/`와 `configs/`가 포함된 새 tag의 build가 완료된다.

### Day 9 Docker 학습 실행

```bash
docker run --rm \
  --user "$(id -u):$(id -g)" \
  --mount type=bind,source="$PWD/logs",target=/app/logs \
  --mount type=bind,source="$PWD/artifacts",target=/app/artifacts \
  mini-ai-ops-lab:day9
```

- 목적: container에서 experiment tracking 학습을 실행하고 결과를 host에 보존한다.
- 변경 여부: host에 success log와 model을 생성하고 종료된 container는 제거한다. image는 유지한다.
- 실행 결과: exit code 0, accuracy 약 96.67%와 `iris-baseline` record가 저장됐고 `artifacts/20260812T004148291974Z-e2bef42e/model.pkl`이 생성됐다.
- 성공 기준: host의 log와 model이 존재하고 현재 WSL 사용자 소유로 생성된다.

### Docker 최근 experiment 조회

```bash
docker run --rm \
  --user "$(id -u):$(id -g)" \
  --mount type=bind,source="$PWD/logs",target=/app/logs,readonly \
  mini-ai-ops-lab:day9 \
  python src/list_runs.py --experiment iris-baseline --limit 3
```

- 목적: Day 9 image의 조회 script가 host run log에서도 동일하게 동작하는지 확인한다.
- 변경 여부: log를 read-only로 연결해 읽기만 하고 종료된 container만 제거한다.
- 실행 결과: exit code 0으로 최신 success, failed, success 세 run이 parameter와 artifact 정보와 함께 출력됐다.
- 성공 기준: 조회 결과가 local과 일치하고 host log가 변경되지 않는다.

### `python src/list_runs.py --help`

- 목적: README의 `--limit`, `--experiment` 설명과 실제 CLI가 일치하는지 확인한다.
- 변경 여부: 도움말만 출력하고 파일을 변경하지 않는다.
- 실행 결과: exit code 0과 두 option 및 기본 limit 5가 출력됐다.
- 성공 기준: 문서에 사용한 option이 CLI 도움말에 존재한다.

## 검증 결과

- 정상 experiment 이름은 기존 parameter와 함께 검증됐고 공백 이름은 학습 전에 거부됐다.
- Success record는 experiment, parameter, metric과 실제 model 경로를 연결했다.
- 설정 검증 후 제어 실패에서도 experiment와 parameter가 유지되고 artifact는 생성되지 않았다.
- 최근 전체 조회는 새 record와 과거 record를 함께 최신순으로 표시했다.
- Experiment filter는 `iris-baseline` run만 정확히 선택했다.
- 잘못된 limit은 exit code 2로 거부됐다.
- Docker 학습은 host에 새 model과 success record를 보존했다.
- Docker의 read-only 조회는 최근 세 run을 변경 없이 출력했다.
- Docker 생성 파일의 소유자는 현재 WSL 사용자와 일치했다.
- README, architecture와 실제 CLI option이 일치했고 Git diff 형식 검사도 통과했다.

  답변: 같은 목적의 학습 실행들을 묶는 식별 이름이다. `experiment_name`은 여러 번 사용할 수 있고, 그 아래의 개별 실행 한 번과 model은 고유한 `run_id`로 구분한다.

## 발견한 문제

- Day 9 이전 JSONL record에는 `experiment_name`과 `parameters`가 없으므로 새 field를 무조건 참조하면 최근 run 조회가 실패하거나 과거 이력을 비교하지 못하는 호환 문제가 있었다.
- 기능 검증을 위해 공백 experiment 이름, 제어된 학습 실패와 잘못된 limit을 의도적으로 실행했으며 모두 계획한 오류 상태로 동작했다.
- 별도의 미해결 기능 오류는 없었다.

## 수정 또는 결정

- Experiment 이름은 grouping label, run ID는 개별 실행 식별자로 역할을 분리했다.
- 비교 편의를 위해 검증된 `config`를 유지하면서 `experiment_name`과 학습 `parameters`를 최상위 field에도 기록했다.
- 과거 record는 없는 값을 `-`로 표시하고 기존 `config`에서 parameter를 보완하되 원본 JSONL을 변경하지 않기로 했다.
- 조회는 최신순으로 표시하고 `deque`를 사용해 filter를 통과한 최근 N개만 memory에 유지한다.
- 일부 JSON line이 손상돼도 다른 운영 이력을 확인할 수 있도록 warning 후 건너뛰기로 했다.
- Docker 조회에서는 host log를 read-only로 mount해 관찰 명령이 운영 기록을 변경하지 않게 했다.

## 회고

사용자의 질문을 통해 `experiment_name`을 개별 학습의 고유 ID로 오해하지 않도록 역할을 분명히 했다. 같은 목적의 여러 실행은 experiment 이름으로 묶고, 각 실행과 model은 run ID로 추적한다. 새 schema를 추가할 때 현재 record만 보는 것이 아니라 이미 쌓인 Day 8 이전 log가 계속 조회되는지도 함께 고려해야 한다는 기준도 확인했다.

## 배운 점

- Experiment tracking은 parameter, metric과 artifact를 같은 run에 연결해야 의미가 있다.
- Experiment 이름은 run을 묶고 run ID는 개별 실행과 model을 식별한다.
- 성공뿐 아니라 실패 record에도 검증된 실험 조건을 남기면 실패 비교가 가능하다.
- Log schema가 확장되면 과거 record의 누락 field를 안전하게 처리해야 한다.
- 최근 N개 조회는 전체 결과를 memory에 쌓지 않고 제한된 queue로 구현할 수 있다.
- 관찰 목적의 Docker mount는 read-only로 지정해 의도하지 않은 log 변경을 막을 수 있다.
