## 코드 및 설정 의도

- `compare_runs.py`는 과거 record를 수정하지 않고 두 success run을 읽기 전용으로 비교한다.
- `load_run_records()`는 run ID로 정확히 하나의 record를 찾도록 하며 중복 ID나 손상된 JSONL을 재현 비교 오류로 처리한다. 재현 판정에서 기록을 조용히 누락하지 않기 위한 결정이다.
- `require_successful_run()`은 parameter, metric과 artifact 경로가 있는 success run만 비교 대상으로 허용한다.
- `compare_runs()`는 같아야 하는 experiment·parameter·metric과 달라야 하는 run ID·artifact 경로를 분리해 검사한다.
- 원본과 재현 artifact는 각각 실제 파일이 존재해야 한다. 현재는 model byte나 모든 예측 결과까지 비교하지 않는다.
- 모든 check가 참이면 `reproduced: true`와 exit code 0, 불일치나 artifact 누락은 exit code 1을 반환한다.
- `docs/runbook.md`는 코드 사용법뿐 아니라 재현 대상 선택, 결과 판단, 실패 시 확인할 항목과 운영상 한계를 함께 설명한다.
- Docker tag는 다시 build할 수 있으므로 image digest처럼 불변 환경 식별자가 아니라는 점을 문서화했다.
- 중요한 함수와 판단에는 사용자가 이해할 수 있는 짧은 한글 docstring과 주석을 사용했다.

## 실행한 명령과 목적

아래 명령은 Day 10 구현 검증을 위해 Codex가 프로젝트 root에서 실행했다. 사용자가 별도로 실행한 것으로 기록하지 않는다.

### 원본 Run 조건 확인

```bash
python -c "import json; from pathlib import Path; from src.config_loader import load_train_config; run_id='20260812T004148291974Z-e2bef42e'; records=[json.loads(line) for line in Path('logs/runs.jsonl').read_text(encoding='utf-8').splitlines()]; record=next(record for record in records if record.get('run_id') == run_id); current=load_train_config('configs/train.yaml'); artifact=Path(record['artifact_path']); print({'status': record['status'], 'config_matches': record['config'] == current, 'metrics': record['metrics'], 'artifact_exists': artifact.is_file()})"
```

- 목적: 선택한 원본의 상태, 기록 설정과 현재 YAML의 일치, metric과 artifact 존재 여부를 확인한다.
- 변경 여부: config, run log와 artifact 경로를 읽기만 한다.
- 실행 결과: exit code 0, `status: success`, `config_matches: true`, `artifact_exists: true`, accuracy 약 96.67%가 확인됐다.
- 성공 기준: 원본이 success이고 설정이 일치하며 model 파일이 존재한다.

### 기존 Success Run으로 비교 도구 검증

```bash

```

- 목적: 실제 재현 실행 전에 비교 도구의 정상 판정 경로를 검증한다.
- 변경 여부: run log와 두 artifact 경로를 읽기만 한다.
- 실행 결과: exit code 0, 모든 check가 `true`, `reproduced: true`가 출력됐다.
- 성공 기준: 같은 조건과 metric의 서로 다른 두 success run을 재현 성공으로 판단한다.

## Codex Q&A

- 질문: Day 10은 config가 생기기 전의 과거 run을 config 이후 형식으로 수정하는 작업인가?
  답변: 아니다. Config가 기록된 Day 9 success run을 그대로 두고 같은 조건의 새 run을 생성해 비교한다. Config가 없는 더 오래된 run은 현재 기록만으로 정확히 재현하기 어렵다.
- 질문: 같은 config라면 같은 결과가 나와야 하는가?
  답변: 현재의 결정적인 Iris 학습에서는 같은 accuracy를 기대한다. 일반적인 머신러닝에서는 data, code, dependency, hardware, random seed와 비결정적 연산도 영향을 주므로 같은 config만으로 결과가 항상 보장되지는 않는다.
- 질문: `compare_runs.py`가 실제 MLOps에서도 필요한가?
  답변: 이 파일 자체는 필수 표준이 아니다. Run의 parameter, metric과 artifact를 비교하는 기능은 MLOps의 핵심이며 실제 환경에서는 MLflow 같은 platform이 그 역할을 대신할 수 있다. 이 프로젝트에서는 원리를 이해하기 위해 작은 script로 구현했다.

## 발견한 문제

- 사용자가 Day 10을 과거 config 없는 record를 수정하는 작업으로 이해할 수 있어, 기존 record 보존과 새 run 생성이라는 범위를 먼저 구분할 필요가 있었다.
- 같은 config가 항상 같은 결과를 보장한다는 인상을 줄 수 있어, 환경과 data도 재현 조건이라는 한계를 명시할 필요가 있었다.
- 현재 run record에는 Git commit, Docker image digest와 data version이 없어 장기적인 완전 재현을 증명할 수 없다.
- 별도의 미해결 기능 오류는 없었다.

## 수정 또는 결정

- Config가 기록된 success run만 현재 재현 대상으로 사용하고 과거 record는 수정하지 않는다.
- 현재 재현 성공 기준을 experiment·parameter·metric 일치, 두 artifact 존재와 서로 다른 실행 식별자로 명확히 정의했다.
- Failed run, 없는 run, 중복 ID와 필요한 field가 없는 record는 비교를 거부한다.
- 같은 Docker tag를 사용하되 tag가 불변 식별자가 아니라는 점을 Runbook과 architecture에 기록했다.
- `compare_runs.py`는 외부 MLOps platform의 run 비교 기능을 학습용으로 단순 구현한 도구로 위치시켰다.

## 회고

이번 작업은 재현을 단순히 같은 명령을 다시 실행하는 것으로 보지 않고, 어떤 값이 같아야 하고 어떤 식별값은 새로 생겨야 하는지 기준을 세우는 과정이었다. 사용자의 질문을 통해 과거 record를 수정하는 migration과 새 run을 만드는 reproduction을 구분했고, config만이 아니라 code·data·dependency·image도 결과에 영향을 준다는 현재 시스템의 한계를 문서에 남겼다.

## 배운 점

- 재현은 원본 기록을 보존하고 새 실행 결과를 비교하는 작업이다.
- 같은 config는 재현에 필요하지만 모든 머신러닝 환경에서 충분조건은 아니다.
- Run ID와 artifact 경로는 새 실행마다 달라야 하고, 비교할 조건과 metric은 같아야 한다.
- 운영 재현 절차에는 실행 명령뿐 아니라 성공 기준과 실패 시 확인 항목이 필요하다.
- Docker tag는 변경 가능하므로 장기 재현에는 image digest가 더 적합하다.
- 실제 MLOps platform은 이 프로젝트의 `compare_runs.py`와 같은 비교 기능을 더 체계적으로 제공한다.
