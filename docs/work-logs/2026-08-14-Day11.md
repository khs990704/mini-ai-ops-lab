## 코드 및 설정 의도

- `tools.yaml`에 존재하는 Tool 이름만 향후 실행 후보가 되도록 allowlist를 코드 밖에 정의했다.
- `echo`는 파일 접근이 없는 `none`, 목록·요약 Tool은 `read`, 학습 Tool은 결과를 생성하는 `write`로 영향 수준을 구분했다.
- `resources`는 각 Tool이 의도상 접근해야 할 project 경로만 명시한다.
- 현재 `run_train_job`은 사용자 입력 없이 기본 학습 설정을 사용하도록 `input_type: none`으로 제한했다.
- `ToolConfig`와 `ToolDefinition`은 검증 후 runner가 기대할 구조를 명시한다.
- `validate_tool_definition()`은 필수·추가 field, 설명, 입력 형태, access와 resource 관계를 검사한다.
- `validate_resource()`는 절대 경로와 `..`를 거부하여 allowlist 설정이 project 밖을 직접 가리키지 않게 한다.
- `load_tool_config()`는 Agent 구분이 없는 현재 단일 실행환경에 공통으로 적용할 검증된 allowlist를 반환한다.
- CLI는 검증된 설정을 JSON으로 출력하고 설정 오류를 exit code 1로 전달해 troubleshooting에 사용할 수 있게 한다.
- 설정 metadata는 실제 요청 차단이나 OS 권한을 자동 적용하지 않으며, Day 12의 runner와 Docker·OS 권한이 함께 실행 경계를 만든다.
- 중요한 함수와 보안 판단은 사용자가 이해할 수 있는 짧은 한글 docstring과 주석으로 설명했다.

## 실행한 명령과 목적

아래 명령은 Day 11 구현 검증을 위해 Codex가 프로젝트 root에서 실행했다. 사용자가 별도로 실행한 것으로 기록하지 않는다.

### Tool Allowlist YAML 구조 확인

```bash
python -c "import yaml; from pathlib import Path; config=yaml.safe_load(Path('configs/tools.yaml').read_text(encoding='utf-8')); tools=config['tools']; assert set(tools) == {'echo', 'list_artifacts', 'read_log_summary', 'run_train_job'}; print({name: {'input_type': item['input_type'], 'access': item['access'], 'resources': item['resources']} for name, item in tools.items()})"
```

- 목적: YAML이 네 Tool과 각 입력·접근 정보를 예상한 자료형으로 해석하는지 확인한다.
- 변경 여부: 설정을 읽고 출력만 하며 Tool, log와 artifact를 생성하지 않는다.
- 실행 결과: exit code 0과 네 Tool의 `none`, `read`, `write` 범위가 출력됐다.
- 성공 기준: Tool 이름 집합과 각 설정값이 `tools.yaml` 정의와 일치한다.

### `python src/tool_config_loader.py --config configs/tools.yaml`

- 목적: 정상 allowlist 전체가 schema와 보안 조건을 통과하는지 확인한다.
- 변경 여부: 설정을 읽고 검증된 JSON을 출력할 뿐 Tool을 실행하지 않는다.
- 실행 결과: exit code 0과 네 Tool의 description, input type, access, resources가 출력됐다.
- 성공 기준: 오류 없이 검증된 `tools` 객체가 반환된다.

### 허용되지 않은 Access 검증

```bash
printf 'tools:\n  bad_tool:\n    description: 잘못된 접근 수준 검증\n    input_type: none\n    access: admin\n    resources: []\n' \
  | python src/tool_config_loader.py --config /dev/stdin
```

- 목적: 정의하지 않은 접근 수준이 allowlist에 들어가지 못하는지 확인한다.
- 변경 여부: 표준입력만 읽고 project 파일을 변경하지 않는다.
- 실행 결과: 예상된 exit code 1과 `access는 다음 중 하나여야 합니다: none, read, write` 오류가 출력됐다.
- 성공 기준: `access: admin`을 검증된 설정으로 반환하지 않는다.

### Project 밖 Resource 경로 검증

```bash
printf 'tools:\n  bad_tool:\n    description: 잘못된 경로 검증\n    input_type: none\n    access: read\n    resources:\n      - ../secret\n' \
  | python src/tool_config_loader.py --config /dev/stdin
```

- 목적: `..`를 이용해 project 밖 resource를 지정하는 설정을 거부한다.
- 변경 여부: 표준입력만 읽고 project 파일을 변경하지 않는다.
- 실행 결과: 예상된 exit code 1과 project 내부 상대 경로만 허용한다는 오류가 출력됐다.
- 성공 기준: 위험한 경로가 검증된 resource로 반환되지 않는다.

### `docker build -t mini-ai-ops-lab:day11 .`

- 목적: Tool allowlist와 loader가 포함된 Day 11 Docker image를 만든다.
- 변경 여부: local Docker image와 build cache를 생성하거나 갱신하며 이전 image는 유지한다.
- 실행 결과: exit code 0으로 `mini-ai-ops-lab:day11` image가 생성됐다.
- 성공 기준: `src/`와 `configs/` 복사 및 image export가 완료된다.

### Docker Allowlist 검증

```bash
docker run --rm \
  mini-ai-ops-lab:day11 \
  python src/tool_config_loader.py --config configs/tools.yaml
```

- 목적: Container에서도 Local과 같은 allowlist를 읽고 검증하는지 확인한다.
- 변경 여부: 기본 학습 명령 대신 설정 검증만 수행하고 종료된 container를 제거한다. Host path를 mount하지 않아 host log와 artifact를 변경하지 않는다.
- 실행 결과: exit code 0과 Local에서 확인한 네 Tool 정의가 동일하게 출력됐다.
- 성공 기준: Container의 검증 결과가 Local 결과와 일치한다.

### `python src/tool_config_loader.py --help`

- 목적: README와 architecture의 설정 검증 명령이 실제 CLI와 일치하는지 확인한다.
- 변경 여부: 도움말만 출력하고 파일을 변경하지 않는다.
- 실행 결과: exit code 0, `--config`와 기본값 `configs/tools.yaml`이 출력됐다.
- 성공 기준: 문서에 안내한 option과 기본 경로가 도움말에 존재한다.

## 검증 결과

- 네 Tool이 예상한 이름, 입력 형태, 영향 수준과 resource로 YAML에서 로드됐다.
- 정상 allowlist는 Local과 Docker 모두 exit code 0으로 검증됐다.
- 지원하지 않는 `access: admin`은 예상된 exit code 1로 거부됐다.
- `../secret` resource는 project 밖 경로 오류와 exit code 1로 거부됐다.
- `access: none` Tool은 resource가 없고 읽기·쓰기 Tool에는 하나 이상의 resource가 있었다.
- Container 검증은 Tool, run log와 model artifact를 생성하지 않았다.
- README, architecture와 실제 CLI가 일치했고 Git diff 형식 검사도 통과했다.

## 직접 확인 방법

검증은 완료됐으므로 반복 실행은 필수가 아니다. Allowlist만 직접 확인하려면 dependency가 준비된 WSL에서 project root로 이동한다.

```bash
cd /home/hskim/project/mini-ai-ops-lab
python src/tool_config_loader.py --config configs/tools.yaml
```

Exit code 0과 `echo`, `list_artifacts`, `read_log_summary`, `run_train_job`의 검증된 JSON이 출력되면 성공이다. 이 명령은 설정만 읽으며 실제 Tool, log와 artifact를 생성하지 않는다.

## Codex Q&A

- 질문: 여기서 Agent는 Codex 같은 도구를 의미하는가?
  답변: Codex는 판단하고 Tool 사용을 요청하는 Agent에 가깝다. 이번에 정의한 네 항목은 Agent가 요청할 수 있는 Tool이며 이 프로젝트 설정이 실제 Codex의 권한을 제한하지는 않는다.
- 질문: Agent마다 Tool 허용 범위는 동일한가, 서로 다른가?
  답변: 둘 다 가능하다. 현재는 Agent identity가 없는 단일 실행환경이라 공통 allowlist를 사용하며, 역할이 나뉘면 Agent 또는 role별 최소 권한으로 확장할 수 있다.
- 질문: 모든 Agent가 같은 allowlist를 공유하는 방식이 더 좋은가?
  답변: Agent 하나와 Tool 네 개를 다루는 현재 학습 단계에서는 단순한 공통 목록이 적합하다. 여러 역할이 생기면 필요 이상의 권한을 막기 위해 역할별로 분리하는 편이 안전하다.
- 질문: 기존 `config_loader.py`는 사용자가 실행하고 `tool_config_loader.py`는 Agent가 사용하는가?
  답변: 사용자와 Agent를 기준으로 나뉜 것이 아니다. 기존 loader는 학습 설정을, 새 loader는 Tool 허용 설정을 검증하며 실제 운영에서는 각각 `run_job.py`와 향후 `tool_runner.py`가 내부에서 사용한다.
- 질문: `tool_config_loader.py`는 Agent가 사용할 Tool을 불러오는 것인가?
  답변: 맞다. 등록된 Tool을 읽고 검증된 공통 allowlist로 반환한다. Loader 자체는 요청을 허용하거나 Tool을 실행하지 않는다.

## 발견한 문제

- Agent와 Tool을 같은 개념으로 이해할 수 있어 요청 주체, 실행 기능과 통제 경계를 구분할 필요가 있었다.
- 공통 allowlist가 항상 최선으로 보일 수 있어 현재 단일 Agent 범위와 향후 역할별 최소 권한 확장을 나눠 설명할 필요가 있었다.
- `access`와 `resources`가 OS 권한을 직접 강제하는 것처럼 보일 수 있어 현재는 정책 metadata라는 경계를 명시했다.
- 기능 검증에서 잘못된 access와 project 밖 경로를 의도적으로 사용했으며 모두 계획한 오류로 처리됐다. 별도의 미해결 기능 오류는 없었다.

## 수정 또는 결정

- Day 11~13의 단일 Agent 실행환경에서는 하나의 공통 allowlist를 사용한다.
- Tool 이름은 shell command가 아니라 향후 미리 구현할 Python handler의 논리적 이름으로 사용한다.
- 영향 수준은 `none`, `read`, `write`로 제한하고 필요한 project resource만 설정에 기록한다.
- 절대 경로와 `..` resource를 loader 단계에서 거부한다.
- 실제 허용·거부와 실행은 Day 12 runner, timeout과 audit log는 Day 13에서 구현한다.
- 여러 Agent 역할이 실제로 필요해질 때 identity와 role별 allowlist로 확장한다.

## 회고

이번 작업에서는 Agent가 Tool 그 자체가 아니라 Tool 사용을 판단하고 요청하는 주체라는 개념을 먼저 구분했다. 사용자의 질문을 통해 공통 allowlist는 현재 작은 단일 Agent 환경에는 적합하지만 실제 역할이 나뉘면 최소 권한에 맞게 분리해야 한다는 확장 기준도 세웠다. 설정을 잘 검증하는 것과 실제 실행 권한을 강제하는 것은 별개의 단계라는 점을 문서에 명확히 남겼다.

## 배운 점

- Agent, Tool과 Tool Runner는 각각 요청 주체, 실행 기능과 통제 경계 역할을 가진다.
- Allowlist는 등록된 Tool만 허용하고 나머지를 기본 거부하는 정책이다.
- 최소 권한은 Tool이 필요한 resource와 영향 수준만 허용하는 원칙이다.
- 공통 allowlist는 단순한 시작점이고 역할이 나뉘면 Agent별 권한이 더 안전할 수 있다.
- 설정 loader는 정책 오류를 검출하지만 실제 요청 차단과 OS 권한 강제는 runner와 실행환경이 담당한다.
- Resource 경로도 입력이므로 절대 경로와 상위 경로 이동을 검증해야 한다.
