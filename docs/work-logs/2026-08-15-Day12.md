# Day 12 - 2026-08-15

## 목표

Agent의 Tool 요청을 실제 allowlist와 비교하고 등록된 Python handler만 실행하는 `src/tool_runner.py`를 구현한다.

## 완료한 작업

- Tool 이름, 선택 입력과 설정 경로를 받는 CLI를 만들었다.
- 요청 이름을 `configs/tools.yaml`의 공통 allowlist와 비교하도록 했다.
- 설정의 `input_type`과 실제 `--input`이 일치하는지 검증했다.
- Tool 이름을 shell command로 실행하지 않고 고정된 Python handler에 연결했다.
- `echo`, `list_artifacts`, `read_log_summary`, `run_train_job` 네 Tool을 구현했다.
- 미등록 Tool, handler가 없는 Tool과 잘못된 입력을 실행 전에 거부하도록 했다.
- 성공과 실패를 동일한 JSON field로 반환하도록 했다.
- Local과 Docker에서 허용된 Tool 실행 및 미등록 Tool 차단을 검증했다.
- README와 architecture에 실제 사용법과 실행 경계를 반영했다.

## 단계별 진행과 검수

1. `tool_runner.py`의 allowlist 검사, 입력 검증과 구조화된 결과를 구현하고 `echo` 실행 및 `unknown` 차단을 검수했다.
2. 읽기 전용 `list_artifacts`와 `read_log_summary` handler를 구현하고 기존 log와 artifact가 변경되지 않는지 확인했다.
3. `run_train_job`을 기존 `run_training_job()`과 연결하고 새 run log와 model artifact 생성을 확인했다.
4. Day 12 Docker image를 만들고 Container에서도 허용 실행과 기본 거부 정책이 같은지 검증했다.
5. 구현 결과와 사용자 질문 검수 후 README, architecture, Agent 실행환경 위키와 Day 12 작업 기록을 정리했다.

## 코드 및 설정 의도

- `ToolResult`는 Agent가 성공과 실패를 같은 `tool_name`, `status`, `result`, `error_type`, `error_message` 구조로 처리하게 한다.
- `ToolNotAllowedError`는 allowlist에 없는 요청을 명확히 구분한다.
- `ToolHandlerNotImplementedError`는 설정에 이름만 추가해도 기능이 실행되지 않도록 별도의 구현 확인 경계를 만든다.
- `validate_tool_input()`은 text 입력의 누락과 입력이 없는 Tool에 전달된 불필요한 값을 기능 실행 전에 차단한다.
- `TOOL_HANDLERS`는 Tool 이름을 검토된 Python 함수에만 연결하며 shell command로 해석하지 않는다.
- `handle_echo()`는 외부 상태를 바꾸지 않고 요청·응답 경로를 확인한다.
- `handle_list_artifacts()`는 `artifacts/*/model.pkl`만 조회해 run ID와 경로를 반환한다.
- `handle_read_log_summary()`는 기존 `load_recent_runs()`를 재사용해 최근 다섯 run의 운영 판단 field만 반환한다.
- `handle_run_train_job()`은 기존 학습 실행기를 재사용하고 Tool 상태와 내부 `training_status`를 구분한다.
- 중요한 실행 통제와 함수 목적은 사용자가 이해할 수 있는 짧은 한글 주석과 docstring으로 설명했다.

## 실행한 명령과 목적

아래 명령은 Day 12 구현 검증을 위해 Codex가 project root에서 실행했다. 사용자가 별도로 실행한 것으로 기록하지 않는다.

### 허용된 Echo Tool 실행

```bash
python src/tool_runner.py --tool echo --input "hello"
```

- 목적: allowlist에 등록되고 handler가 구현된 text Tool이 실행되는지 확인한다.
- 변경 여부: 설정만 읽고 문자열을 반환하며 project 파일을 변경하지 않는다.
- 실행 결과: exit code `0`, `status: success`, `result: "hello"`가 반환됐다.
- 성공 기준: 요청 이름과 입력이 그대로 구조화된 성공 JSON에 표시된다.

### 미등록 Tool 차단

```bash
python src/tool_runner.py --tool unknown
```

- 목적: allowlist에 없는 이름이 handler 실행 전에 기본 거부되는지 확인한다.
- 변경 여부: Tool, log와 artifact를 생성하지 않는다.
- 실행 결과: 예상된 exit code `1`과 `ToolNotAllowedError`가 구조화된 실패 JSON으로 반환됐다.
- 성공 기준: 미등록 이름이 실행되지 않고 `status: failed`로 구분된다.

### Artifact 목록 조회

```bash
python src/tool_runner.py --tool list_artifacts
```

- 목적: 저장된 model artifact의 run ID와 경로를 Tool로 조회한다.
- 변경 여부: `artifacts/`를 읽기만 한다.
- 실행 결과: 초기 검증에서 기존 artifact 14개, 학습 Tool 검증 후 회귀 검사에서 15개가 반환됐다.
- 성공 기준: 실제 `model.pkl` 개수와 반환된 `count` 및 경로가 일치한다.

### 최근 Run 요약 조회

```bash
python src/tool_runner.py --tool read_log_summary
```

- 목적: 최근 학습의 성공·실패, accuracy, 오류와 artifact 경로를 빠르게 확인한다.
- 변경 여부: `logs/runs.jsonl`을 읽기만 한다.
- 실행 결과: exit code `0`과 최근 run 다섯 개가 최신순으로 반환됐다.
- 성공 기준: `count: 5`와 각 run의 핵심 field가 구조화된 JSON에 존재한다.

### 입력이 없는 Tool의 잘못된 입력 차단

```bash
python src/tool_runner.py --tool list_artifacts --input unexpected
python src/tool_runner.py --tool run_train_job --input unexpected
```

- 목적: `input_type: none` Tool이 입력을 받았을 때 상태 변경 전에 차단하는지 확인한다.
- 변경 여부: 두 요청 모두 조회나 학습 handler를 호출하지 않는다.
- 실행 결과: 각각 예상된 exit code `1`과 `Tool은 --input을 받지 않습니다` 오류가 반환됐다.
- 성공 기준: 잘못된 요청이 artifact나 run log를 생성하지 않는다.

### 학습 Tool 실행

```bash
python src/tool_runner.py --tool run_train_job
```

- 목적: 쓰기 권한으로 정의한 Tool이 기존 학습 실행기와 연결되는지 확인한다.
- 변경 여부: model을 학습하고 run log 한 줄과 artifact 하나를 생성한다.
- 실행 결과: exit code `0`, run ID `20260815T070644302424Z-1584d7ea`, `training_status: success`, accuracy `0.9666666666666667`이 반환됐다.
- 성공 기준: `logs/runs.jsonl`의 마지막 record와 `artifacts/20260815T070644302424Z-1584d7ea/model.pkl`이 같은 run ID로 연결된다.

### Day 12 Docker Image 생성

```bash
docker build -t mini-ai-ops-lab:day12 .
```

- 목적: Tool Runner가 포함된 재현 가능한 Day 12 실행환경을 만든다.
- 변경 여부: local Docker image와 build cache를 생성하거나 갱신한다.
- 실행 결과: exit code `0`으로 `mini-ai-ops-lab:day12` image가 생성됐다.
- 성공 기준: source와 config 복사, non-root 사용자 준비와 image export가 완료된다.

### Docker Tool 실행과 차단

```bash
docker run --rm mini-ai-ops-lab:day12 python src/tool_runner.py --tool echo --input "hello"
docker run --rm mini-ai-ops-lab:day12 python src/tool_runner.py --tool run_train_job
docker run --rm mini-ai-ops-lab:day12 python src/tool_runner.py --tool unknown
docker run --rm mini-ai-ops-lab:day12 python src/tool_runner.py --tool list_artifacts
```

- 목적: Container에서도 같은 allowlist, handler와 기본 거부 정책이 적용되는지 확인한다.
- 변경 여부: 각 명령은 일회성 Container를 만들고 종료 후 제거한다. Host path를 mount하지 않아 Container 학습 결과는 host에 저장되지 않는다.
- 실행 결과: `echo`, `run_train_job`, `list_artifacts`는 exit code `0`, `unknown`은 예상된 exit code `1`을 반환했다.
- 성공 기준: Container 학습은 내부에서 성공하고, 미등록 요청은 차단되며, 새 Container의 artifact 목록은 비어 있다.

## 검증 결과

- 네 allowlist Tool이 Local에서 모두 의도한 handler로 실행됐다.
- 미등록 Tool과 잘못된 입력은 기능 실행 전에 exit code `1`로 거부됐다.
- 성공과 실패 모두 같은 JSON envelope를 사용했다.
- Local `run_train_job`은 새 run log와 model artifact를 실제로 생성했다.
- 읽기 전용 Tool은 기존 log와 artifact를 변경하지 않았다.
- Day 12 Docker image에서도 허용 실행과 미등록 Tool 차단 결과가 Local과 같았다.
- Mount가 없는 Container 학습의 run과 artifact는 host 결과에 섞이지 않았다.
- CLI 도움말, Python 문법과 Git diff 형식 검사가 exit code `0`으로 통과했다.

## 직접 확인 방법

검증은 완료됐으므로 반복 실행은 필수가 아니다. 직접 확인하려면 dependency가 준비된 WSL의 project root에서 다음 명령을 실행한다.

```bash
cd /home/hskim/project/mini-ai-ops-lab
python src/tool_runner.py --tool echo --input "hello"
python src/tool_runner.py --tool list_artifacts
python src/tool_runner.py --tool read_log_summary
python src/tool_runner.py --tool unknown
```

앞의 세 명령은 project 상태를 변경하지 않는다. `unknown`은 의도적으로 exit code `1`을 반환하며 `ToolNotAllowedError`가 보이면 차단 성공이다.

새 학습까지 직접 확인할 때만 다음 명령을 추가로 실행한다.

```bash
python src/tool_runner.py --tool run_train_job
```

이 명령은 반복할 때마다 `logs/runs.jsonl`에 한 줄과 `artifacts/{run_id}/model.pkl` 하나를 추가한다. 반환된 `run_id`, `training_status: success`와 실제 artifact 경로가 일치하면 성공이다.

## 발견한 문제

- Day 11의 설정과 loader만으로는 Agent 요청이 실제로 허용된 Tool만 사용하는지 검증되지 않았다.
- Allowlist에 이름이 있다는 사실만으로 실행하면 설정 변경이 곧 코드 실행 권한이 될 수 있었다.
- 입력이 없는 Tool에 값이 전달되면 의도하지 않은 handler 동작 가능성을 실행 전에 막을 필요가 있었다.
- Tool 실행 성공과 Tool 내부 학습 성공이 모두 `status`로 표현되면 두 실행 계층을 혼동할 수 있었다.
- Docker 검증 결과를 host에 mount하면 검증용 log와 artifact가 local 결과에 추가될 수 있었다.

## 수정 또는 결정

- 요청 이름이 allowlist와 고정 `TOOL_HANDLERS` 양쪽에 존재할 때만 실행한다.
- Tool 이름을 shell 명령으로 해석하지 않고 Python 함수에 직접 연결한다.
- 설정의 `input_type`을 handler 호출 전에 검증한다.
- Tool 호출 상태는 바깥 `status`, 학습 상태는 `result.training_status`로 구분한다.
- 읽기 요약은 현재 운영 확인에 충분한 최근 다섯 run으로 제한한다.
- Docker 기능 검증은 host mount 없이 수행해 검증 결과를 Container 안에 격리했다.
- Timeout과 모든 요청의 audit log는 Day 13 범위로 유지했다.

## 회고

이번 작업은 “허용할 Tool을 설정에 정의하는 것”과 “그 정책을 실제 요청에 강제하는 것”이 서로 다른 단계라는 점을 코드로 연결했다. 사용자의 질문을 기준으로 Tool별 목적을 짧게 구분하고, 중앙 runner가 이름·입력·handler를 순서대로 검사하는 구조를 확인했다. 현재는 실행 자체를 통제하지만 실행 시간과 요청 이력은 남기지 않으므로 다음 단계의 timeout과 audit log가 필요하다.

## 배운 점

- Allowlist는 runner가 요청마다 확인할 때 실제 실행 통제가 된다.
- 설정 등록과 고정 handler 구현을 분리하면 설정만으로 임의 코드가 실행되는 것을 막을 수 있다.
- 입력 검증은 handler 호출 전에 수행해야 상태 변경 가능성을 줄일 수 있다.
- 읽기 Tool과 쓰기 Tool은 project에 미치는 영향과 검증 방법이 다르다.
- 구조화된 결과는 Agent와 CLI가 성공·실패를 같은 field로 처리하게 한다.
- Tool 호출 결과와 Tool 내부 job 결과는 별도의 상태로 구분할 수 있다.
- Mount가 없는 일회성 Container 결과는 종료 시 제거되므로 host 결과 보존 여부를 의도적으로 선택해야 한다.
