## 실행한 명령과 목적

아래 명령은 Day 14 검수를 위해 Codex가 project root에서 실행했다. 모두 기존 데이터를 읽기만 했으며 새 run, audit record 또는 artifact를 만들지 않았다.

### Log 수량과 상태 확인

```bash
python -c "import json; from pathlib import Path; paths={'runs':'logs/runs.jsonl','audit':'logs/audit.jsonl'}; logs={name:[json.loads(line) for line in Path(path).read_text(encoding='utf-8').splitlines() if line.strip()] for name,path in paths.items()}; print({name:{'count':len(records),'statuses':sorted({record.get('status') for record in records})} for name,records in logs.items()})"
```

- 목적: 두 JSONL 파일의 모든 줄이 JSON으로 해석되고 예상 상태값을 사용하는지 확인한다.
- 변경 여부: 읽기 전용이다.
- 실행 결과: exit code `0`; run 17건은 `failed`, `success`, audit 10건은 `failed`, `success`, `timeout` 상태를 사용했다.
- 성공 기준: JSON decode 오류 없이 각 log의 건수와 허용된 상태 집합이 출력된다.

### Success Run과 Model 연결 확인

```bash
python -c "import json; from pathlib import Path; records=[json.loads(line) for line in Path('logs/runs.jsonl').read_text(encoding='utf-8').splitlines() if line.strip()]; success=[record for record in records if record.get('status') == 'success']; missing=[record.get('run_id') for record in success if not record.get('artifact_path') or not Path(record['artifact_path']).is_file()]; print({'success_runs':len(success),'missing_artifacts':missing})"
```

- 목적: 모든 성공 학습 record가 실제 model artifact를 가리키는지 확인한다.
- 변경 여부: 읽기 전용이다.
- 실행 결과: exit code `0`; `success_runs`는 12, `missing_artifacts`는 빈 목록이었다.
- 성공 기준: 누락된 artifact의 run ID가 출력되지 않는다.

### Run Log Schema 세대 확인

```bash
python -c "import json, collections; from pathlib import Path; records=[json.loads(line) for line in Path('logs/runs.jsonl').read_text(encoding='utf-8').splitlines() if line.strip()]; groups=collections.Counter(tuple(sorted(record)) for record in records); print([{'count':count,'fields':fields} for fields,count in groups.items()])"
```

- 목적: 기능 추가 전후의 run record가 어떤 field 조합으로 남아 있는지 확인한다.
- 변경 여부: 읽기 전용이다.
- 실행 결과: exit code `0`; Day 4 형식 2건, 오류 field 추가 형식 6건, config 추가 형식 3건, experiment·parameters 추가 형식 6건으로 구분됐다.
- 성공 기준: 각 record가 JSON object이고 schema 변화가 설명 가능한 세대로 묶인다.

### CLI 진입점 확인

```bash
python src/run_job.py --help
python src/tool_runner.py --help
python src/list_runs.py --help
python src/compare_runs.py --help
```

- 목적: 문서에 안내한 네 실행 진입점과 주요 option이 실제 CLI에 존재하는지 확인한다.
- 변경 여부: 도움말만 표시하는 읽기 전용 명령이다.
- 실행 결과: 네 명령 모두 exit code `0`이었다. `run_job.py`는 `--config`, `--fail`; `tool_runner.py`는 `--tool`, `--input`, `--config`, `--timeout`; 조회 도구는 limit·experiment 또는 비교할 두 run option을 표시했다.
- 성공 기준: usage가 출력되고 log나 artifact 수가 증가하지 않는다.

## 수정 또는 결정

## 회고

오늘은 기능을 추가하는 날이라기보다 지금까지 만든 두 흐름을 하나의 시스템 관점에서 확인하는 날로 구분했다. 기존 로그와 새 로그의 field 차이에 관한 질문을 통해, 과거 record의 누락 field를 손상으로 보지 않고 기능 추가에 따른 schema evolution으로 해석해야 한다는 점을 확인했다. 원본 이력을 보존하면서 조회와 검증 코드가 여러 세대를 처리하는 방식이 현재 프로젝트에 더 적합하다.

## 배운 점

- 직접 학습과 Agent Tool 학습은 진입점이 다르지만 같은 학습 운영 함수를 재사용한다.
- Run log는 학습 결과를, audit log는 Tool 요청을 설명하며 `run_train_job`에서는 두 증거가 함께 남는다.
- 구조화된 로그도 기능이 진화하면 과거와 현재 record의 field가 다를 수 있다.
- Schema 차이만으로 과거 데이터를 손상으로 판단하면 안 되며 생성 시점과 호환 정책을 함께 봐야 한다.
- Success record에서 artifact로 가는 연결뿐 아니라 artifact에서 log로 돌아오는 역방향 연결도 검수할 가치가 있다.
- 서로 다른 log를 정확히 연결하려면 공통 `request_id`나 `run_id` 같은 상관관계 식별자가 필요하다.
