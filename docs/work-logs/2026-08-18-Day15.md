# Day 15 - 2026-08-18

## 목표

학습과 Agent Tool 실행에서 발생할 수 있는 다섯 장애를 안전하게 재현하고, 증상·로그·원인·복구·예방 절차를 운영자가 사용할 수 있는 문서로 완성한다.

## 완료한 작업

- 기존 학습 실패와 Tool timeout 시나리오를 현재 구현에 맞게 검수했다.
- 존재하지 않는 설정 파일을 지정해 config load 실패와 failed run 기록을 확인했다.
- 실제 filesystem을 손상시키지 않고 `save_model()`에 제어된 `OSError`를 주입해 artifact 저장 실패를 검증했다.
- Allowlist에 없는 Tool 요청이 실행 전에 차단되고 failed audit record로 남는지 확인했다.
- 다섯 장애에 목적, 안전한 재현법, 증상, 확인할 기록, 원인, 복구와 예방 항목을 갖췄다.
- 장애별 빠른 판단표와 공통 대응 순서를 추가했다.
- 실제 run·audit log에서 다섯 장애의 오류 증거를 확인했다.
- 실패 시나리오의 의미와 미허용 Tool 대응 원칙을 기술 위키에 분류했다.

## 단계별 진행과 검수

1. Config load 실패를 문서화하고 `FileNotFoundError` failed run과 artifact 미생성을 검수했다.
2. Model artifact 저장 실패를 문서화하고 제어된 `OSError`가 failed run으로 남으며 model 수가 증가하지 않는지 검수했다.
3. 미허용 Tool 요청을 문서화하고 `ToolNotAllowedError` audit record만 추가되며 run과 model은 변하지 않는지 검수했다.
4. 학습 실패, artifact 저장 실패, Tool timeout, config load 실패와 미허용 Tool 요청의 형식·코드·로그 연결을 전체 검수했다.
5. 모든 구현 단계와 사용자 질문 검수 후 로깅·Agent 실행환경 위키와 Day 15 작업 기록을 정리했다.

## 코드 및 설정 의도

Day 15에는 실행 source와 설정을 변경하지 않았다. 이미 구현된 오류 처리 기능을 검증하고 다음 문서를 현재 동작에 맞게 완성했다.

- `docs/failure-scenarios.md`: 장애마다 재현에서 복구까지 같은 구조로 찾을 수 있게 하고, 빠른 판단표와 공통 대응 순서로 초기 확인 시간을 줄인다.
- Config load 시나리오: 설정 검증 전 실패에서는 요청 경로만 남고 검증된 config·parameter·metric·artifact가 모두 `null`임을 설명한다.
- Artifact 저장 시나리오: 학습 계산이 끝났어도 model을 보존하지 못하면 전체 run은 실패이며, 실제 쓰기 장애에는 빈 디렉터리나 일부 파일이 남을 수 있음을 설명한다.
- 미허용 Tool 시나리오: Allowlist와 고정 handler의 이중 확인을 유지하고, 단순히 YAML에 이름을 추가하는 것을 복구로 취급하지 않는다.
- `docs/wiki/logging-monitoring.md`: 제어된 실패, 검증 명령의 exit code와 내부 run 상태의 차이, 실패 record 보존 원칙을 설명한다.
- `docs/wiki/agent-runtime.md`: 미등록 요청의 차단·audit 기록과 올바른 요청 수정 절차를 설명한다.

## 실행한 명령과 목적

아래 장애 재현 명령은 Day 15 검증을 위해 Codex가 project root에서 실행했다. 사용자가 별도로 실행한 것으로 기록하지 않는다.

### Config Load 실패 재현

```bash
python src/run_job.py --config configs/missing.yaml
```

- 목적: 존재하지 않는 설정 파일을 읽지 못해도 요청 경로와 실패 원인이 run log에 남는지 확인한다.
- 변경 여부: `logs/runs.jsonl`에 failed record 한 줄을 추가하며 학습과 model 저장은 실행하지 않는다.
- 실행 결과: 예상된 exit code `1`, run ID `20260818T042028775125Z-9a55db94`, `FileNotFoundError`와 `config: null`, `artifact_path: null`이 기록됐다.
- 성공 기준: 요청한 `configs/missing.yaml` 경로와 오류가 기록되고 model artifact 수가 증가하지 않는다.

### Model Artifact 저장 실패 재현

```bash
python -c "import json; from unittest.mock import patch; from src.run_job import run_training_job; patcher=patch('src.run_job.save_model', side_effect=OSError('검증을 위해 발생시킨 artifact 저장 실패입니다.')); patcher.start(); record=run_training_job(); patcher.stop(); print(json.dumps(record, ensure_ascii=False, sort_keys=True)); raise SystemExit(0 if record['status'] == 'failed' and record['error_type'] == 'OSError' else 1)"
```

- 목적: 권한이나 disk를 실제로 손상시키지 않고 학습 후 model 저장 exception 처리 경로를 검증한다.
- 변경 여부: 현재 Python process의 `save_model()`만 임시 교체하고 source는 바꾸지 않는다. `logs/runs.jsonl`에 failed record 한 줄을 추가하며 model은 만들지 않는다.
- 실행 결과: 검증 명령 exit code `0`, run ID `20260818T042402745576Z-488e2808`, 내부 run의 `status: failed`, `error_type: OSError`, `artifact_path: null`이 확인됐다.
- 성공 기준: 여기서 명령 exit code `0`은 학습 성공이 아니라 예상한 failed record와 오류 종류가 정확히 만들어졌다는 뜻이다. Model artifact는 16개로 유지됐다.

### 미허용 Tool 요청 재현

```bash
python src/tool_runner.py --tool forbidden_command
```

- 목적: Allowlist에 없는 이름이 handler 실행 전에 차단되고 거부 시도가 audit log에 남는지 확인한다.
- 변경 여부: 임의 기능, run과 model은 실행하지 않고 `logs/audit.jsonl`에 failed record 한 줄을 추가한다.
- 실행 결과: 예상된 exit code `1`, `status: failed`, `ToolNotAllowedError`; audit log는 10건에서 11건으로 증가했다. Run log는 20건, model은 16개로 유지됐다.
- 성공 기준: `forbidden_command`가 실행되지 않고 이름, 실패 상태, 오류와 제한 시간이 audit record에 존재한다.

### 전체 오류 증거 확인

```bash
python -c "import json; from collections import Counter; from pathlib import Path; runs=[json.loads(line) for line in Path('logs/runs.jsonl').read_text(encoding='utf-8').splitlines() if line.strip()]; audits=[json.loads(line) for line in Path('logs/audit.jsonl').read_text(encoding='utf-8').splitlines() if line.strip()]; print({'run_failure_evidence':dict(Counter(record.get('error_type') for record in runs if record.get('status') == 'failed')),'audit_failure_evidence':dict(Counter(record.get('error_type') for record in audits if record.get('status') != 'success'))})"
```

- 목적: 현재 JSONL에 다섯 장애를 뒷받침하는 오류 종류가 존재하는지 한 번에 확인한다.
- 변경 여부: 두 log를 읽기만 한다.
- 실행 결과: run log에는 `RuntimeError` 5건, `FileNotFoundError` 2건, `OSError` 1건이 있었고 audit log에는 `ToolNotAllowedError` 3건, `ToolTimeoutError` 2건이 있었다.
- 성공 기준: 모든 JSONL이 해석되고 다섯 시나리오의 대표 오류가 빠짐없이 집계된다.

정상 복구 명령은 `docs/failure-scenarios.md`에 정확한 예상 결과와 부작용을 작성했지만, 검증이 끝난 뒤 불필요한 success run, model과 audit record를 더 만들지 않기 위해 별도로 실행하지 않았다.

## Codex Q&A

- 질문: 실패 시나리오를 만들어 실제 실패 시 오류 메시지를 확인할 수 있도록 하는 것인가?
  답변: 맞다. 다만 오늘 새 오류 처리 기능을 만드는 것이 아니라 기존 `run_job.py`와 `tool_runner.py`의 실패 경로를 안전하게 재현해 terminal, run log 또는 audit log에서 무엇을 확인하고 어떻게 정상 상태로 복구할지 문서화하는 작업이다.
- 질문: 장애 시나리오는 실무에서도 이런 오류가 발생하기 때문에 추가한 것인가?
  답변: 맞다. 학습·data 오류, disk·권한 문제, 잘못된 config, 멈추거나 느린 Tool과 정책 밖 요청은 실제 MLOps 운영에서도 발생한다. 이번에는 project를 손상시키지 않도록 실제 원인이 아닌 제어된 방법으로 같은 처리 경로를 확인했다.
- 질문: 테스트용 시나리오일 뿐인가, 실제 이 project로 MLOps 작업을 할 때의 장애에 대비한 것인가?
  답변: 두 역할을 모두 가진다. 개발 단계에는 오류 처리와 log를 검증하는 failure testing이고, 운영 단계에는 실제 장애에서 확인할 log, 일부 결과와 복구 순서를 제공하는 대응서다. 다만 OS 강제 종료, log write 실패, network storage와 부분 파일 같은 환경 장애까지 이번 검증이 모두 보장하지는 않는다.

## 발견한 문제

- Artifact 저장 실패를 실제 권한 제거나 disk 고갈로 재현하면 project와 다른 작업에 영향을 줄 수 있다.
- 실제 `save_model()`은 run 디렉터리를 만든 뒤 model을 바로 쓰므로 중간 실패 시 빈 디렉터리나 불완전한 파일이 남을 수 있다.
- 제어된 artifact 검증 명령은 예상한 내부 실패를 찾으면 exit code `0`을 반환하므로, 이를 학습 성공으로 오해할 수 있다.
- Timeout은 process를 중단하지만 이미 발생한 run log, artifact 또는 외부 상태를 자동으로 되돌리지 않는다.
- 미허용 Tool 요청도 audit record를 추가하므로 반복적인 거부 요청은 log 증가 원인이 될 수 있다.
- Log rotation과 과도한 log 증가는 아직 별도 장애 시나리오로 완성하지 않았다.
- OS가 memory 부족으로 process를 강제 종료하거나 log 파일 자체를 쓸 수 없는 경우에는 현재 Python exception 처리로 failed record를 보장할 수 없다.

## 수정 또는 결정

- 실제 filesystem 권한이나 disk 상태를 변경하지 않고 `unittest.mock.patch`로 저장 함수에 `OSError`를 주입했다.
- 검증 프로그램의 exit code와 내부 run의 `status`를 문서에서 명시적으로 구분했다.
- 실패 기록은 성공처럼 수정하지 않고 장애 증거로 보존하며, 복구는 원인 해결 후 새 run을 만드는 방식으로 정했다.
- 미등록 Tool은 기본 거부하고, 새 Tool이 필요할 때만 정책과 고정 handler를 함께 검토하도록 했다.
- 복구용 정상 실행 명령은 문서화하되 불필요한 결과 생성을 피하기 위해 이번 검증에서는 실행하지 않았다.
- 빠른 판단표와 공통 대응 순서를 문서 앞부분에 배치했다.
- 장애 문서를 안전한 failure testing과 실제 운영 대응서의 두 용도로 명시하고, 제어된 재현이 보장하지 않는 환경 장애를 구분했다.

## 회고

사용자의 질문을 통해 실패 시나리오는 오류 메시지를 단순히 모아 두는 문서가 아니라, 장애를 안전하게 재현하고 어떤 운영 증거를 확인할지와 복구 방법까지 검증하는 절차라는 점을 구분했다. 또한 테스트 문서와 실제 운영 대응서는 별개가 아니라, 안전한 failure testing으로 현재 대응 절차를 확인하고 그 결과를 운영에 사용하는 관계임을 정리했다. 실제 장애를 무리하게 만들지 않으면서 동일한 exception 처리 경로를 확인하는 방식이 project 안전성과 반복 가능성에 적합하지만, OS·filesystem 수준 장애는 추가 검증이 필요하다.

## 배운 점

- 장애 시나리오는 재현, 관찰, 원인 판단, 복구와 예방을 하나의 흐름으로 연결한다.
- 학습 장애는 run log, Agent Tool 장애는 audit log를 먼저 확인한다.
- `error_type`은 오류 분류, `error_message`는 구체적 설명, `traceback`은 발생 위치와 호출 경로를 보여준다.
- Config 검증 전 실패는 사용된 config가 없으므로 관련 field가 `null`이다.
- 학습이 끝났어도 model 저장에 실패하면 정상 artifact가 없으므로 전체 run은 failed다.
- 제어된 exception 주입은 실제 운영환경을 손상시키지 않고 실패 처리 경로를 반복 검증할 수 있다.
- 검증 명령의 성공과 검증 대상 내부 작업의 성공은 서로 다른 상태일 수 있다.
- 미허용 Tool은 실행하지 않지만 거부 요청 자체는 감사 증거로 남긴다.
- 복구는 과거 failed record를 바꾸는 것이 아니라 원인을 해결하고 새 success 실행을 만드는 과정이다.
- 현재 다섯 장애는 실제 MLOps에서 발생할 수 있는 유형이며 재현 방법만 안전한 검증용으로 바꾼 것이다.
- Failure testing은 운영 대응을 검증하는 수단이지만 실제 환경의 모든 강제 종료와 부분 실패를 자동으로 보장하지 않는다.
