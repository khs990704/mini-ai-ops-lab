## 발견한 문제

- 기존 Runbook은 이전 run 재현 중심이라 환경 준비, 기본 실행, 전체 장애 복구와 cleanup 절차가 부족했다.
- `python src/config_loader.py --config configs/train.yaml`은 exit code `0`이지만 출력 없이 끝났다. 이 파일은 직접 실행 CLI가 아니라 import용 module이라 loader를 호출하지 않았다.
- 기존 재현 사전 조건은 Docker를 항상 필수로 설명해 Local 재현 가능성을 구분하지 않았다.
- Docker image를 점검하는 절차는 있었지만 기본 image 실행 방법이 재현 예시에만 있었다.
- `docker ps -a`에는 이 project와 무관한 종료 container도 함께 나타나 일괄 정리가 위험했다.
- 현재 run record만으로 원본의 Git commit과 Docker image를 확정할 수 없어 완전한 실행환경 재현에는 한계가 있다.

- Config 검증은 `load_train_config()`를 명시적으로 호출하고 JSON을 출력하는 명령으로 교체했다.
- Local과 Docker를 선택 가능한 실행환경으로 구분하고 각각의 조건과 상태 변화를 설명했다.

- Docker는 host mount가 없는 smoke test와 결과를 보존하는 mount 실행을 분리했다.
- 장애 복구는 기존 failed record를 수정하지 않고 원인을 해결한 뒤 새 success 실행으로 판단하도록 했다.
- Cleanup은 읽기 전용 점검을 먼저 하고 다른 project container나 참조 관계가 불명확한 artifact를 자동 삭제하지 않도록 했다.
- Day 17의 backup·retention 기준이 정해지기 전에는 현재 log와 model을 운영 증거로 보존한다.

## 회고

사용자의 질문을 통해 Day 16은 장애 대응 문서만 확장하는 날이 아니라 기존 기능 전체를 실제 운영 순서로 연결하는 날임을 구분했다. 새 코드를 작성하지 않더라도 문서의 명령을 실제 실행하면 잘못된 진입점이나 빠진 Docker 사용 경로를 발견할 수 있었다. 기능이 존재하는 것과 운영자가 안전하게 반복 사용할 수 있는 것은 서로 다른 완성 기준이다.

## 배운 점

- Runbook은 정상 운영과 장애 대응에서 실행할 명령의 순서를 제공한다.
- 명령마다 읽기 전용인지 log·artifact·Docker 상태를 바꾸는지 알아야 한다.
- Import용 module은 exit code `0`으로 끝나도 직접 실행 기능이 동작한 것은 아닐 수 있다.
- Local과 Docker는 같은 code를 사용하지만 결과 보존과 실행환경 조건이 다르다.
- Docker의 `--rm`과 host mount 유무에 따라 container 결과의 보존 여부가 달라진다.
- 재현 실행은 원본을 바꾸는 것이 아니라 새 run과 model을 만든 뒤 비교하는 작업이다.
- 복구는 오류가 사라진 것뿐 아니라 새 success 상태와 기대한 결과물로 판단한다.
- 오래됐거나 종료됐다는 이유만으로 다른 project container와 운영 증거를 삭제하면 안 된다.
- 운영 문서는 기존 기능을 검증 가능한 절차로 만드는 project 결과물이다.
