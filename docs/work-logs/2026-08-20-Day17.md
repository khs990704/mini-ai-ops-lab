# Day 17 - 2026-08-20

## 실행한 명령과 목적

아래 명령은 Day 17 검증을 위해 Codex가 project root에서 실행했다. 사용자가 별도로 실행한 것으로 기록하지 않는다.

### Git 제외와 Secret 보조 검사

```bash
git check-ignore -v .env logs/runs.jsonl artifacts/example/model.pkl
git ls-files .env .env.example logs artifacts
git grep -nE 'AKIA[0-9A-Z]{16}|BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY'
```

- 목적: 실제 Secret·운영 결과가 Git 제외 규칙에 해당하고, 공유 가능한 placeholder만 추적되는지 확인한다.
- 변경 여부: Git 규칙과 추적 파일을 읽기만 한다.
- 실행 결과: `.env`, run log와 model 예시 경로는 ignore 대상이었다. 추적 대상은 `.env.example`, `logs/.gitkeep`, `artifacts/.gitkeep`이었고 명확한 Secret pattern은 검출되지 않았다.
- 성공 기준: 제외 경로가 해당 규칙과 함께 출력되고 Secret 검색은 결과 없이 exit code `1`이다.

### 접근 권한과 현재 사용량 확인

```bash
stat -c '%a %U:%G %n' \
  .env.example configs/train.yaml configs/tools.yaml \
  logs artifacts logs/runs.jsonl logs/audit.jsonl
find logs artifacts -type f -perm /022 -print
docker image inspect mini-ai-ops-lab:day13 \
  --format '{{.Config.User}} {{.Config.WorkingDir}}'
du -sh logs artifacts
wc -l logs/runs.jsonl logs/audit.jsonl
```

- 목적: 주요 파일의 소유자와 mode, 다른 사용자에게 쓰기가 허용된 운영 파일, Docker 실행 사용자와 backup 판단용 저장량을 확인한다.
- 변경 여부: 권한, image metadata와 파일 사용량을 읽기만 한다.
- 실행 결과: 주요 file은 `644`, directory는 `755`, 소유자는 `hskim:hskim`이었다. Group·other writable 운영 파일은 없었고 Docker는 `appuser /app`을 사용했다. Logs는 `28K`, artifacts는 `144K`, run은 21건, audit은 12건이었다.
- 성공 기준: 의도하지 않은 writable 파일이 출력되지 않고 전용 Docker 사용자와 예상 경로가 표시된다.

### Archive 생성과 별도 경로 복원

```bash
mktemp -d /tmp/mini-ai-ops-backup-test.XXXXXX
mkdir /tmp/mini-ai-ops-backup-test.ZlqkE5/restored
tar -czf /tmp/mini-ai-ops-backup-test.ZlqkE5/mini-ai-ops-data.tar.gz \
  configs logs artifacts
tar -tzf /tmp/mini-ai-ops-backup-test.ZlqkE5/mini-ai-ops-data.tar.gz
tar -xzf /tmp/mini-ai-ops-backup-test.ZlqkE5/mini-ai-ops-data.tar.gz \
  -C /tmp/mini-ai-ops-backup-test.ZlqkE5/restored
```

- 목적: 충돌하지 않는 시험 directory를 만든 뒤 config, log와 model을 한 archive로 backup하고 원본과 분리된 위치에서 restore한다.
- 변경 여부: Project 원본은 변경하지 않고 `/tmp`에 archive와 복원 파일을 생성한다.
- 실행 결과: `8.0K` archive에 세 directory가 포함됐고 생성·목록 확인·복원이 모두 exit code `0`으로 끝났다.
- 성공 기준: Archive 목록에 보호 대상이 표시되고 `restored/` 아래에 같은 구조가 생성된다.

### 원본·복원본과 실제 형식 검증

```bash
diff -rq configs /tmp/mini-ai-ops-backup-test.ZlqkE5/restored/configs
diff -rq logs /tmp/mini-ai-ops-backup-test.ZlqkE5/restored/logs
diff -rq artifacts /tmp/mini-ai-ops-backup-test.ZlqkE5/restored/artifacts
sha256sum \
  configs/train.yaml \
  /tmp/mini-ai-ops-backup-test.ZlqkE5/restored/configs/train.yaml \
  logs/runs.jsonl \
  /tmp/mini-ai-ops-backup-test.ZlqkE5/restored/logs/runs.jsonl
find /tmp/mini-ai-ops-backup-test.ZlqkE5/restored/artifacts \
  -name model.pkl -type f | wc -l
python -c 'import json; from pathlib import Path; paths = [Path("/tmp/mini-ai-ops-backup-test.ZlqkE5/restored/logs/runs.jsonl"), Path("/tmp/mini-ai-ops-backup-test.ZlqkE5/restored/logs/audit.jsonl")]; print({str(path): sum(1 for line in path.read_text(encoding="utf-8").splitlines() if json.loads(line)) for path in paths})'
python -c 'from src.config_loader import load_train_config; print(load_train_config("/tmp/mini-ai-ops-backup-test.ZlqkE5/restored/configs/train.yaml"))'
```

- 목적: 파일이 풀린 것만 확인하지 않고 원본과 byte 단위로 같으며 log와 config를 실제 code가 읽을 수 있는지 확인한다.
- 변경 여부: 원본과 복원본을 읽기만 한다.
- 실행 결과: 세 `diff`는 출력 없이 exit code `0`이었다. 대표 config와 run log의 checksum이 각각 일치했고 model 17개, run 21건, audit 12건이 복원됐다. JSONL parsing과 config 검증도 성공했다.
- 성공 기준: `diff` 차이가 없고 checksum·개수와 parsing 결과가 원본과 같다.

Archive SHA-256은 `817f68bb13ddd011d8b77d951d3516125e3e206184648c3d71bb66405b8e596f`였다. 시험 파일은 `/tmp/mini-ai-ops-backup-test.ZlqkE5`에 남겼지만 임시 경로이므로 실제 장애용 backup으로 간주하지 않는다.

### 복구 후 읽기 전용 상태 확인

```bash
python -c "from src.config_loader import load_train_config; print(load_train_config('configs/train.yaml'))"
python src/list_runs.py --limit 3
tail -n 3 logs/audit.jsonl
find artifacts -maxdepth 2 -type f -name 'model.pkl' -printf '%p %s bytes\n' | sort
```

- 목적: Config, 최근 run·audit와 model이 운영 코드에서 읽히는지 확인한다.
- 변경 여부: 모두 읽기 전용이며 새 log나 model을 만들지 않는다.
- 실행 결과: 학습 설정 검증, 최근 run 조회, audit 조회와 17개 model 확인이 모두 성공했다.
- 성공 기준: 모든 명령이 exit code `0`이고 예상 record와 0 byte보다 큰 model이 표시된다.

## 검증 결과

- `.env`, 실제 log와 model은 Git 제외 규칙에 해당했다.
- Git 추적 파일에서 고신뢰 Secret pattern이 발견되지 않았다.
- Docker는 root가 아닌 `appuser`로 실행되며 운영 파일에 group·other 쓰기 권한이 없었다.
- 원본과 복원본의 `configs/`, `logs/`, `artifacts/`에 차이가 없었다.
- 복원 model 17개와 JSONL run 21건·audit 12건이 확인됐다.
- 복원된 학습 config가 기존 loader 검증을 통과했다.
- 관련 문서 경로와 Markdown diff 형식 검사가 통과했다.
- 검증을 위해 project log, artifact, source와 config를 변경하지 않았다.

## 직접 확인 방법

검증은 완료됐으므로 backup을 다시 만들 필요는 없다. 현재 문서와 운영 data 상태만 확인하려면 WSL project root에서 다음 읽기 전용 명령을 실행한다.

```bash
cd /home/hskim/project/mini-ai-ops-lab
sed -n '1,220p' docs/security-backup-checklist.md
python src/list_runs.py --limit 3
du -sh logs artifacts
```

- 첫 명령은 작업 위치를 project root로 이동한다.
- `sed`는 체크리스트 앞부분을 출력하고 파일을 변경하지 않는다.
- `list_runs.py`와 `du`는 최근 run과 backup 대상 크기를 읽기만 한다.
- 성공 기준은 문서, 최근 run 표와 두 directory 크기가 오류 없이 출력되는 것이다.

실제 backup·restore를 다시 시험하려면 체크리스트의 Backup·restore 검증 절차를 같은 terminal에서 순서대로 실행한다. 이 절차는 project 원본을 덮어쓰지 않지만 `/tmp`에 새 시험 directory와 archive를 생성한다. `/tmp` 결과물은 system 정리나 재시작 때 사라질 수 있다.

## Codex Q&A

- 질문: RPO와 RTO는 무엇인가?
  답변: RPO는 장애 시 최대 얼마만큼의 최근 data 손실을 허용할지, RTO는 장애 후 얼마 안에 다시 사용할 수 있어야 할지를 정한 목표다. 이 project의 초기 기준은 RPO 24시간과 RTO 2시간이다.
- 질문: Day 17도 문서화 작업인가?
  답변: 주 결과물은 보안·백업 문서지만 실제 Git 제외, 권한, Docker 사용자와 저장량을 점검하고 archive 생성·복원까지 검증한다.
- 질문: SLA가 무엇이며 왜 RPO·RTO와 다른가?
  답변: SLA는 외부 고객에게 서비스 수준을 보장하는 약속이다. 현재 project에는 SLA가 없고 RPO·RTO는 backup·restore 연습을 위한 내부 목표다.
- 질문: 2단계에서는 기준점을 정한 것인가?
  답변: 맞다. 보존 기간, backup 주기, 접근 권한, 허용 data 손실과 목표 복구 시간의 초기 기준을 정했다. 자동화가 완료됐다는 뜻은 아니다.
- 질문: Backup할 때 무엇을 보관하는가?
  답변: 현재 archive에는 학습·Tool 설정인 `configs/`, 실행·감사 기록인 `logs/`, model인 `artifacts/`를 넣는다. Source와 문서는 Git에서 복구하고 Secret은 일반 archive에서 제외한다.

## 발견한 문제

- RPO, RTO, SLA와 daily·weekly 보관 수가 처음에는 한꺼번에 제시돼 각 용어가 어떤 기준인지 이해하기 어려웠다.
- 기존 Architecture와 Runbook에는 backup 정책이 아직 없거나 Day 17에 정할 예정이라는 오래된 설명이 남아 있었다.
- `/tmp` backup은 원본과 같은 host에 있어 host 장애에 대비한 실제 backup 역할을 하지 못한다.
- 현재 backup, rotation과 외부 저장소 전달은 자동화되지 않았다.
- 현재 WSL의 file `644`, directory `755`는 다른 local 사용자의 읽기를 허용하므로 다중 사용자 server에는 그대로 적용하기 어렵다.

## 수정 또는 결정

- RPO를 “최근 data를 얼마까지 잃어도 되는가”, RTO를 “얼마나 빨리 되살려야 하는가”라는 질문으로 설명했다.
- SLA가 없는 학습 project이며 RPO 24시간·RTO 2시간은 내부 기준임을 명시했다.
- `Daily 7개`, `Weekly 4개`는 보관할 archive 수이고 아직 자동화되지 않았다고 설명했다.
- Git, 운영 data archive와 Secret 저장소의 복구 역할을 분리했다.
- Backup은 생성만 하지 않고 staging 경로 복원, 원본 비교, JSONL parsing과 config 검증까지 완료해야 성공으로 판단했다.
- Secret 노출 시 파일 삭제보다 credential 폐기·회전을 먼저 수행하도록 정했다.
- Architecture, Runbook과 README를 현재 체크리스트에 연결했다.

## 회고

질문을 통해 RPO·RTO 같은 약어보다 실제 운영 질문인 “얼마나 잃을 수 있는가”와 “얼마나 빨리 복구할 것인가”가 기준을 이해하는 데 더 직접적이라는 점을 확인했다. 또한 무엇을 backup하는지 구분하면서 Git, 운영 data archive와 Secret 저장소가 서로 다른 복구 역할을 가진다는 구조를 명확히 했다. 문서 기준은 실제 archive를 만들고 복원본을 읽어 봤을 때 비로소 현재 project에서 실행 가능한 절차인지 확인할 수 있었다.

## 배운 점

- RPO는 허용 가능한 data 손실 구간이고 RTO는 목표 복구 시간이다.
- SLA는 고객과 맺는 보장 약속이므로 내부 학습 목표인 RPO·RTO와 다르다.
- Backup 대상은 Git에서 복구할 source, archive로 복구할 운영 data와 별도로 보호할 Secret으로 나눌 수 있다.
- Archive 생성 성공만으로 복구 가능성을 증명할 수 없으며 별도 경로 restore와 내용 검증이 필요하다.
- JSONL은 각 줄 parsing, model은 파일 수·크기·checksum과 신뢰할 수 있는 출처를 함께 확인해야 한다.
- Secret이 노출되면 history에서 지우기 전에 credential을 폐기하거나 회전해야 한다.
- 현재 수동 절차와 기준이 있다는 것과 자동 backup이 구현됐다는 것은 다르다.
- 같은 host의 `/tmp`는 복원 시험에는 유용하지만 실제 host 장애용 backup 위치는 아니다.
